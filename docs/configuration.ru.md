# Справочник конфигурации

[English version](configuration.en.md)

Здесь описаны переменные окружения из `.env` и связанные с ними поля
`config/config.yaml`. Файл `.env` создаётся копированием `.env.example` и
исключён из Git. Для Compose обязательна только переменная
`POSTGRES_PASSWORD`; остальные переменные необязательны. Токены платформ
намеренно хранятся не в `.env`, а в `secrets/telegram_token` и
`secrets/vk_token` с правами `0600`. `ASTRO_DB_PASSWORD` внутри контейнера
приложения автоматически получает значение `POSTGRES_PASSWORD` и отдельно не
задаётся.

## Среда выполнения и доступ

| Переменная | Обязательна | Рекомендуемое значение | Эффект |
|---|---|---|---|
| `POSTGRES_PASSWORD` | Да | Уникальная случайная строка длиной от 32 символов | Пароль PostgreSQL и приложения. После инициализации БД его смена требует также сменить пароль роли внутри PostgreSQL. |
| `POSTGRES_DB` | Нет | `bot_astrosferum` | Имя базы PostgreSQL. Для штатного Compose-развёртывания лучше оставить значение по умолчанию. |
| `POSTGRES_USER` | Нет | `bot_astrosferum` | Имя роли PostgreSQL. Для штатного Compose-развёртывания лучше оставить значение по умолчанию. |
| `ASTRO_TELEGRAM_ADMIN_IDS` | Нет | Числовые ID через запятую или пустая строка | Открывает `/admin` и статистику в Telegram. Статистику не фильтрует: администратор видит общие итоги Telegram + VK. |
| `ASTRO_VK_ADMIN_IDS` | Нет | Числовые VK ID через запятую или пустая строка | Открывает админку и статистику в VK. Нужны числовые ID пользователей, а не screen name; отчёт общий для Telegram + VK. |
| `ASTRO_LIGHT_POLLUTION_ATLAS_YEAR` | Нет | `2024` | Фиксирует проверенный оператором годовой Light Pollution Atlas; автоматического перехода на новый год нет. Менять следует только после проверки и загрузки поддерживаемого набора. |
| `ASTRO_FORECAST_CONCURRENCY` | Нет | `2` | Общий максимум одновременно рассчитываемых обычных прогнозов для Telegram, VK и сайта. Остальные запросы ожидают в той же очереди. |
| `ASTRO_ICON_DOWNLOAD_LIMIT_MBIT` | Нет | Не задана | Общий предел в десятичных Мбит/с для одновременных загрузок ICON-EU и ICON Global. Отсутствующее, пустое значение или `0` означает отсутствие ограничения. |
| `ASTRO_GEOS_CF_ENABLED` | Нет | `true` | Включает независимое обогащение AOD550/озоном NASA GEOS-CF только для ночного эталона полосы V. Отключённый, устаревший, медленный или недоступный источник убирает кольцо, но не меняет и не останавливает основной прогноз Overall по ICON. |

Связанные параметры источника задаются в YAML, потому что описывают внешний
набор данных, а не пользовательскую калибровку:

```yaml
providers:
  geos_cf:
    enabled: true
    dataset_url: https://opendap.nccs.nasa.gov/dods/gmao/geos-cf/v2/fcst/xgc_tavg_1hr_glo_L1440x721_slv.latest
    request_timeout: 60s
    metadata_cache_ttl: 10m
    data_cache_ttl: 6h
    max_stale_age: 48h
    cache_entries: 256
```

Тайм-аут HTTP позволяет холодному запросу OPeNDAP закончиться и заполнить
ограниченный кеш в ОЗУ. После готовности данных ICON приложение ждёт не более
пяти дополнительных секунд; затем строит прогноз без кольца эталона V, а
принадлежащая службе операция может продолжаться не более 65 секунд. При
остановке бота она отменяется. Число уникальных загрузок точечных выборок
ограничено без ожидания значением `ASTRO_FORECAST_CONCURRENCY`, а одинаковые
запросы объединяются в одну операцию: медленный внешний источник не создаёт
неограниченную фоновую очередь. Обновление метаданных обнаруживает новое
опорное время состава атмосферы, а ключ кеша изображений включает версии
алгоритма/полосы и все интерполированные значения AOD/озона, поэтому новый
набор данных или новая формула не получит старое изображение.

Штатный Compose всегда передаёт `ASTRO_GEOS_CF_ENABLED`, подставляя `true` при
отсутствии значения. Поэтому для отключения поставщика в Compose следует
задать `ASTRO_GEOS_CF_ENABLED=false` в `.env`. Одного `enabled: false` в YAML
достаточно при прямом запуске, когда переменная окружения отсутствует.

## Необязательный анализ горизонта по ICON-EU

Этот более тяжёлый анализ доступен только тогда, когда для точки выбран
ICON-EU. В прогнозе ICON Global кнопка этого действия не показывается.
В production он делит с астрокуполом одну ограниченную directional FIFO и общий
настраиваемый лимит активных слотов; workers обычного прогноза остаются
независимыми. Для rollout рекомендуется одна активная тяжёлая задача.

| Переменная | Обязательна | Рекомендуемое значение | Эффект |
|---|---|---|---|
| `ASTRO_HORIZON_ANALYSIS_ENABLED` | Нет | `true` | Переопределяет `horizon_analysis.enabled`. При `false` приложение не инициализирует источник Horizon и не показывает кнопку действия. Общая directional FIFO может продолжать обслуживать астрокупол; обычный прогноз из семи графиков не затрагивается. |
| `ASTRO_HORIZON_CONCURRENCY` | Нет | `1` | Legacy-граница конструктора Horizon. Оставьте `1`: production scheduling задаётся только `ASTRO_DIRECTIONAL_CONCURRENCY` и не зависит от `ASTRO_FORECAST_CONCURRENCY`. |

Bundled Compose всегда задаёт эту переменную и подставляет `true`, если её нет
в `.env`. Поэтому в Compose значение из окружения всегда имеет приоритет над
YAML: для отключения нужно записать
`ASTRO_HORIZON_ANALYSIS_ENABLED=false` в `.env`. Одного `enabled: false` в YAML
достаточно только при прямом запуске вне Compose, когда переменная окружения
действительно отсутствует.

Эксплуатационные ограничения задаются в `config/config.yaml`:

```yaml
horizon_analysis:
  enabled: true
  queue_size: 4
  concurrency: 1
  cdo_workers: 8
  job_timeout: 10m
  cache_ttl: 48h
  cache_entries: 128
  estimated_duration: 3m
```

| Поле YAML | Рекомендуемое значение | Эффект |
|---|---:|---|
| `enabled` | `true` | Включает функцию только для ICON-EU, если environment override отсутствует. При `false` очередь и источник не запускаются, кнопка действия отсутствует. В bundled Compose следует использовать описанную выше переменную окружения. |
| `queue_size` | `4` | Устаревшее ограничение локального конструктора. Production admission ограничивает `directional.queue_size`; это поле не создаёт вторую очередь. |
| `concurrency` | `1` | Устаревшее ограничение локального конструктора. Оставьте `1`; оно не увеличивает concurrency общего production worker. |
| `cdo_workers` | `8` | Общий лимит CDO subprocesses (`1..16`) изолированного directional worker; оба runner используют именно это значение. Horizon строит один reusable weight plan на запрос; Astrodome проверяет сетку каждого исходного сообщения и использует `gennn` только для сбора целей с точными нативными индексами перед собственной билинейной реконструкцией. До переиспользования плана доказываются SCRIP-адреса и побитово точные единичные веса. Обычный ICON-EU прогноз выполняет `grib_get -l` и этим лимитом не управляется. |
| `job_timeout` | `10m` | Максимальное время выполнения одного задания анализа горизонта, после которого оно отменяется. |
| `cache_ttl` | `48h` | Максимальный возраст готового результата, при котором его ещё можно повторно использовать из кеша. Просроченные записи удаляются при старте, периодически во время работы обработчика и при публикации в кеш. |
| `cache_entries` | `128` | Максимальное число готовых результатов в ограниченном кеше анализа горизонта. |
| `estimated_duration` | `3m` | Показываемая пользователю оценка длительности. Она не меняет тайм-аут или планирование обработчика и не гарантирует время завершения. |

Рекомендуемые ограничения следует менять только по результатам измерения
нагрузки. Включение функции не делает её доступной для точек ICON Global.

## Общий directional worker и астрокупол

«Горизонт» и направленный атмосферный астрокупол используют один coordinator,
одну bounded FIFO и
один изолированный worker service. Число активных слотов задано явно и должно
совпадать у bot coordinator, worker и операторского CLI. До измерений памяти,
CPU и задержки обычного прогноза для полного купола следует оставить один слот.

| Переменная | Обязательна | Рекомендуемое значение | Эффект |
|---|---|---|---|
| `ASTRO_DIRECTIONAL_QUEUE_SIZE` | Нет | `8` | Максимум ожидающих задач «Горизонт» + астрокупол. Заполненная FIFO отклоняет admission; одинаковые identity могут разделить один расчёт. |
| `ASTRO_DIRECTIONAL_CONCURRENCY` | Нет | `1` до измерений | Общий лимит активных расчётов «Горизонт» + астрокупол; допустимо `1..32`. Каждый дополнительный слот астрокупола может занять весь resident limit, поэтому bot, worker и операторский CLI должны получать одинаковое значение, а cgroup- и disk-бюджеты нужно повторно проверить до увеличения. |
| `ASTRO_ASTRODOME_ENABLED` | Нет | `true` после rollout | Переключатель публичного доступа, а не выключатель worker. `true` разрешает доступ всем авторизованным через Telegram OIDC; `false` — только `ASTRO_TELEGRAM_ADMIN_IDS`; `false` и пустой список запрещают всем. |
| `ASTRO_ASTRODOME_RESIDENT_LIMIT` | Нет | `10GiB` | Максимальный прогнозируемый resident footprint предзагруженных исходных колонок ICON-EU для одной задачи астрокупола. Validation принимает `1GiB..20GiB`; значение должно быть ниже жёсткого cgroup-лимита worker с запасом для Go, CDO/ecCodes и учитываемого file cache. |
| `ASTRO_ASTRODOME_JOB_TIMEOUT` | Нет | `0s` | Предельное время расчёта астрокупола. `0s` отключает его, чтобы живой расчёт не отменялся по оценочному времени; положительное значение должно находиться в диапазоне `1m..1h`. Явная отмена пользователем и остановка процесса продолжают действовать. |
| `ASTRO_DIRECTIONAL_INTERNAL_REQUEST_TIMEOUT` | Нет | `0s` | Тайм-аут внутреннего HTTP-запроса bot→worker. `0s` отключает транспортный обрыв; положительное значение должно находиться в диапазоне `1s..8h`. При отключённом тайм-ауте задачи оно также должно быть `0s`, а при конечном — превышать его. |
| `ASTRO_DIRECTIONAL_WORKER_MEMORY_LIMIT` | Нет | `24g` до измерений | Жёсткий Compose/cgroup-лимит для Go, дочерних CDO/ecCodes и учитываемого file cache. Это консервативный кандидат, а не измеренный минимум. |
| `ASTRO_DIRECTIONAL_WORKER_GOMEMLIMIT` | Нет | `12GiB` до измерений | Цель Go heap внутри жёсткого лимита worker; это не лимит всего процесса/cgroup. |
| `ASTRO_DIRECTIONAL_WORKER_CPU_LIMIT` | Нет | `8.00` на production-хосте с 12 потоками | CPU-квота Compose для изолированного worker. При одном directional-слоте четыре логических CPU остаются для синхронизации модели и обычных прогнозов. Перед переносом этого значения на другой хост нужен новый замер. |

Связанные значения YAML:

```yaml
directional:
  queue_size: 8
  concurrency: 1
  completed_ttl: 48h
  completed_entries: 128
  estimated_horizon: 3m
  estimated_astrodome: 30m
  internal_request_timeout: 0s
astrodome:
  enabled: true
  job_timeout: 0s
  cache_ttl: 48h
  cache_entries: 64
  resident_limit: 10GiB
  project_disk_cap: 400GiB
  min_free_space: 100GiB
  min_free_inodes: 10000
```

Короткий измерительный прогон показал `244,151 с` для предзагрузки 300 колонок
при четырёх CDO workers и `0,969…1,423 с` на один научный узел. Для 129 узлов
`production-v2` это даёт проекцию полного расчёта `22,8…33,1 мин` и целевой
эксплуатационный диапазон не более 30–35 минут, но не измеренное конечное время
72-кадрового продукта. Поэтому `30m` — только оценка очереди и интерфейса, а не
SLA и не предел выполнения. В production оба ограничения — тайм-аут задачи
астрокупола и тайм-аут HTTP bot→worker — равны `0s`, поэтому живой расчёт не
обрывается по оценочному времени. Явная отмена, остановка координатора и
остановка процесса по-прежнему распространяются через контекст запроса.
Оператор может задать конечные пределы в указанных выше диапазонах: транспортный
предел тогда должен превышать предел задачи и не может оставаться конечным при
отключённом пределе задачи. Исторический baseline v28/path-v22 охватил все 9 288
узло-часов за 33 мин 14 с: 9 284 доступны, четыре физических интервала короче
GL2 закрылись с ошибкой. Один такой прогон не заменяет повторные cold/warm
измерения CPU/RSS/диска и payload, одновременную синхронизацию модели и
наблюдательную валидацию. Готовые результаты ограничены TTL
и числом записей. Admission также учитывает staging, leases, временные данные,
потолок всего проекта, свободные bytes и inode. Queue size ограничивает
ожидающие задачи, а directional concurrency — выполняемые; одно не выводится из
другого. Полный dense-volume отображается в расчётный профиль `production-v2`;
версионированный `sparse-storage-v1` выбирается только из-за бюджета
хранилища, а исторический `dense-v1` не является production-профилем. Режим
доступа не переопределяет решение `DiskBudget`: при выключенном публичном
доступе администраторы не получают принудительный sparse-профиль. До повторных
успешных cold/warm прогонов снижать лимиты worker или вводить конечные
тайм-ауты нельзя.

## Интеграция с отдельным сайтом

Публичное приложение, OIDC, сессии, настройки, каталог сохранённых
визуализаций, браузерный рендерер, edge-конфигурация и их переменные
окружения принадлежат отдельному репозиторию
[site-astrosferum](https://github.com/Haeniken/site-astrosferum). Бот не
читает переменные `ASTRO_WEB_*`.

Этот deployment по-прежнему владеет PostgreSQL и научным runtime. Он отдаёт
только аутентифицированный внутренний API кабинета через существующие
directional gateway и credential. Web-задачи обычного прогноза и «Горизонта»
возвращают принадлежащие пользователю статус и версионированный интерактивный
JSON, который хранится 96 часов; они используют настроенные очереди, точно
сохраняют подготовленные научные значения, не растеризуют PNG при website-only
cache miss и не отправляют сообщения в платформы. Forecast JSON закрепляет
`overall-astronomy-index-v2-fog-heuristic-availability`, `effective-cloud-obstruction-v1` и SHA-256 полной
калибровки Overall, использованной для результата. Сайт может использовать отдельную роль
PostgreSQL с минимальными правами, но его остановка или удаление не должны
влиять на Telegram, VK, синхронизацию моделей, обычный прогноз,
«Горизонт» или расчёт астрокупола. Политика доступа сайта должна совпадать с
`ASTRO_ASTRODOME_ENABLED` и `ASTRO_TELEGRAM_ADMIN_IDS`; рассогласование
закрывается на границе API бота.

## Общая калибровка Overall, Horizon и астрокупола

Остальные необязательные переменные образуют единую калибровку для Overall
Astronomy Index, опционального индекса направлений Horizon и астрокупола. Значения ниже —
рекомендуемый production-профиль репозитория. Их следует менять как единый
проверенный набор, а не подстраивать по одной без повторной валидации. Полная
калибровка входит в каждый ключ кеша Horizon/астрокупола. Схема расчётного
запроса Astrodome v3 передаёт SHA-256 канонической полной калибровки, worker
отклоняет несовпадение digest между bot и worker, а dataset сохраняет тот же
digest как provenance. Поэтому после изменения старый результат не
переиспользуется. Некорректные или противоречивые значения
останавливают приложение на этапе проверки конфигурации.

| Переменная | Рекомендуется | Эффект |
|---|---:|---|
| `ASTRO_OVERALL_SEEING_WEIGHT` | `1.0` | Показатель степени для качества оптического сиинга; увеличение сильнее штрафует посредственный сиинг. |
| `ASTRO_OVERALL_CLOUD_WEIGHT` | `2.0` | Показатель степени для модельного пропускания облаков; увеличение усиливает влияние облачной преграды. |
| `ASTRO_OVERALL_COHERENCE_TIME_WEIGHT` | `0.25` | Ограниченный вес чувствительного к ветру времени когерентности `tau0`; `0` отключает этот guard, `1` применяет его полностью. |
| `ASTRO_OVERALL_OPTICAL_TURBULENCE_MAX_PENALTY` | `0.25` | Максимальная совокупная потеря от utility-члена seeing/`tau0`. Он оставляет множитель не ниже `0.75` и не обрезает физические показатели. |
| `ASTRO_OVERALL_POSSIBLE_FOG_FACTOR` / `ASTRO_OVERALL_HIGH_FOG_FACTOR` | `0.75` / `0.10` | Множители для возможного/высокого предупреждающего уровня `FogHeuristic`. Чем меньше значение, тем сильнее штраф; это не калиброванные вероятности тумана. |
| `ASTRO_OVERALL_PRECIPITATION_DETECT_MM` | `0.05` | Порог обнаружения детерминированных почасовых осадков. При достижении порога обычный Overall применяет бинарный эксплуатационный запрет и возвращает индекс 1; интенсивность намеренно не превращается в плавный штраф. Поле остаётся частью общей калибровки и ключа кеша, но текущий направленный расчёт Horizon осадки не получает. |
| `ASTRO_OVERALL_GOOD_SEEING_ARCSEC` / `ASTRO_OVERALL_BAD_SEEING_ARCSEC` | `0.5` / `2.0` | Хорошая и плохая опорные границы для логарифмического преобразования модельного сиинга в качество. |
| `ASTRO_OVERALL_BEST_COHERENCE_TIME_MS` / `ASTRO_OVERALL_BAD_COHERENCE_TIME_MS` | `5.2` / `1.6` | Хорошая и плохая опорные границы преобразования `tau0` в корректирующий множитель. |
| `ASTRO_OVERALL_BOUNDARY_LAYER_MIN_M` / `ASTRO_OVERALL_BOUNDARY_LAYER_TOP_M` | `500` / `2000` | Нижнее и верхнее ограничения глубины перемешанного слоя ICON для гибридного интеграла турбулентности TKE + HMNSP99. |
| `ASTRO_OVERALL_GROUND_CN2_SCALE` | `1.0` | Множитель приземного `Cn2`; значения выше `1` усиливают вклад модельной турбулентности у поверхности. |
| `ASTRO_OVERALL_UNRESOLVED_CLOUD_OBSTRUCTION` | `0.45` | Максимальный guard нижней облачности, если диагностический `CLC` не представлен разрешёнными `QC/QI`; для среднего и верхнего ярусов применяются меньшие фиксированные доли. |
| `ASTRO_OVERALL_SURFACE_WIND_MAX_PENALTY` | `0.20` | Максимальный относительный штраф за приземный ветер/порывы; `0.20` оставляет от этого guard множитель не ниже `0.80`. |
| `ASTRO_OVERALL_SURFACE_WIND_START_MS` / `ASTRO_OVERALL_SURFACE_WIND_FULL_MS` | `8.5` / `15.0` | Скорости устойчивого ветра, при которых мягкий штраф начинается и достигает заданного максимума. |
| `ASTRO_OVERALL_SURFACE_GUST_START_MS` / `ASTRO_OVERALL_SURFACE_GUST_FULL_MS` | `12.0` / `22.0` | Скорости порывов, при которых тот же штраф начинается и достигает максимума. |
| `ASTRO_CLOUD_LIQUID_RADIUS_MICROMETERS` / `ASTRO_CLOUD_ICE_RADIUS_MICROMETERS` | `10` / `25` | Принятые эффективные радиусы капель/кристаллов для преобразования водности в видимую оптическую толщину. Меньший радиус даёт более сильное ослабление при той же массе конденсата. |
