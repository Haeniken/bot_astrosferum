Дата: 2026-07-22

## Готово

- PostgreSQL 18.4 хранит пользователей, до 10 точек на пользователя и ограниченные 90 днями суточные агрегаты запросов;
- клавиатуры Telegram и VK поддерживают сохранение/выбор точек; администраторы платформ из `.env` получают общее число учётных записей и единый PNG по запросам обеих платформ за 30 дней;
- Light Pollution Atlas 2024 дополнен отдельным сравнением World Atlas 2015; обязательный GeoTIFF автоматически восстанавливается при старте;
- runtime использует официальный OSGeo GDAL 3.13.1 и ecCodes 2.45.0.
- имена полей поверхности нормализуются между версиями ecCodes (`VMAX_10M`/`max_i10fg`);
- админский график использует составные столбцы «успешно/с ошибкой» и календарные сутки MSK (UTC+3); меню точек имеют кнопку «Назад».

- Go `1.26.5`, `tzf v1.2.3`, `gonum/plot v0.17.0`;
- Telegram принимает native location, а VK — geo-вложение; обе платформы принимают `59.9386, 30.3141` и `/forecast 59.9386 30.3141`;
- оба тонких platform adapter зависят от общего обработчика `internal/app/bot` и не импортируют друг друга; VK Group Long Poll включается при старте, сообщения и geo приводятся к общему запросу, а тексты, клавиатуры, PNG-фото и документы без потери качества переводятся в вызовы VK API;
- Telegram и VK работают под независимыми перезапускающими supervisor, поэтому сбой API одной платформы не останавливает синхронизацию моделей и вторую платформу;
- обычные прогнозы имеют общий межплатформенный лимит расчётов и после занятия двух настроенных слотов сообщают место в очереди; у Horizon остаются собственная ограниченная очередь и независимо настраиваемое число workers;
- VK photo/document upload проверяет handshake и делает не более двух повторов с паузами `1 с`/`2 с` и новым upload URL; это обрабатывает временные `405` или неполные ответы `pu.vk.ru` без бесконечных retry;
- между последовательными media-delivery одного VK-запроса действует минимальный интервал `150 мс` без общей блокировки; параллельные VK-запросы и отправка Telegram не менялись;
- `/start` и `/help` объясняют запрос и интерпретацию всех семи графиков;
- пользовательское сообщение показывает выбранную модель, run ID и возраст model run относительно настраиваемого `max_stale_age`; этот порог управляет только предупреждением `⚠️ stale run` и не удерживает данные в кеше. Run ID входит в ключи point/render cache, поэтому новый опубликованный run автоматически даёт cache miss;
- язык Telegram определяется по `User.language_code`: только `ru*` получает русский интерфейс, любой другой или отсутствующий код — английский; локализованы помощь, статусы, ошибки, кнопки, подписи, погодная таблица и все заголовки/оси/легенды PNG, а render-cache разделён по языку;
- VK пока использует русский по умолчанию, поскольку Group Long Poll не передаёт аналог Telegram `language_code`;
- timezone определяется offline по координатам и подписывается на каждом PNG;
- DWD discovery выбирает последний полный ICON-EU цикл `00/06/12/18` с доступным `+72 h`;
- координаты вне домена ICON-EU маршрутизируются на последний полный ICON Global `00/06/12/18` на полной native global grid; CDO использует официальную статическую геометрию DWD для выбора ближайшего native-узла без обрезки источника и без второй мировой raster-копии;
- ICON Global теперь синхронизирует тот же 79-часовой 27-уровневый контракт `CLC/P/T/QC/QI + нижние U/V/TKE + HHL`, что ICON-EU, используя эквивалентные по высоте model indices со сдвигом `+46`; DWD Global TKE заканчивается на `+48 ч`, поэтому до него bundle содержит 187 сообщений/час, затем 169, cloud map остаётся полной, а гибридный Overall заканчивается без экстраполяции отсутствующей турбулентности; прямой `VIS` также остаётся недоступен в DWD Global feed;
- atomic sync скачивает pressure-level `U/V/FI/T`, не сохраняет `.bz2`, проверяет каждый бандл через ecCodes и SHA-256;
- старый pressure-level run атомарно дополняется только отсутствующими `FI/T`; scheduler независимо публикует versioned hourly surface/cloud bundle, а ecCodes 2.45 `clwmr/QI` нормализуются во внутренние `qc/qi`;
- ICON-EU и ICON Global оставляют предыдущий полный `current` доступным, пока загружаются все компоненты нового run; `current` переключается одной атомарной symlink-операцией только после полной проверки;
- sync защищён exclusive lock; scheduler запускает проверку при старте, затем каждые 15 минут и хранит два последних run; пользовательский запрос ничего не скачивает, а читает последний полностью опубликованный набор;
- point extractor параллельно получает 25 вертикальных профилей из текущего manifest;
- независимый surface sync публикует 79 почасовых бандлов `f000…f078` с `T_2M`, `TD_2M`, `RELHUM_2M`, `CLCT/CLCL/CLCM/CLCH`, `TOT_PREC`, `U_10M`, `V_10M`, `VMAX_10M`, `PMSL`, `VIS`, `TQV` и точными столбовыми `TQC/TQI`;
- обе платформы показывают 72 часа; туман берётся из прямого `VIS`, а карта облаков показывает эффективную преграду по высоте из `CLC+QC+QI` и фазовой оптической толщины;
- роса показывается только как подсказка о подготовке обогрева/бленды и не снижает seeing или практический score;
- pure-Go astronomy рассчитывает Солнце, Луну, Юпитер и Сатурн; регрессии для Санкт-Петербурга и Москвы ограничивают Sun/Moon двумя минутами от эталона, а события планет явно помечены как приближённые;
- обе платформы отправляют одинаковые семь PNG; production-индекс `3200×960` объединяет гибридный ICON TKE/MH + HMNSP99 seeing, `tau0`, эффективное облачное пропускание по `CLCT+TQC+TQI`, туман и мягкий приземный ветер;
- текстовый блок получает точечную оценку засветки из Light Pollution Atlas 2024: билинейные LPI/SQM на сетке около `30″` и честно помеченный ориентир Бортля; засветка не входит в Overall Index;
- значения в heatmap увеличены до 8 pt и сделаны полужирными, оси и bar labels также увеличены;
- старый wind-only index сохранён отдельным диагностическим графиком; direction delta равен `0°` при ветре `<2 m/s`, а `NaN` означает только отсутствие данных;

## Анализ «Горизонт» — реализован

Опциональный анализ «Горизонт» является существующей функцией приложения и
управляется параметром `ASTRO_HORIZON_ANALYSIS_ENABLED`. Он намеренно доступен только
после обычного прогноза ICON-EU и охватывает полный неизменяемый интервал
`f000..f072`. Для ICON Global нет ни кнопки, ни запускаемой задачи «Горизонт».
Реализация включает:

- environment/configuration switch с валидацией и disabled-путём, которому не
  требуются operational limits Horizon;
- небольшой общий versioned action router и нормализованные callback events
  Telegram/VK; в platform adapters нет формул Horizon; composition root уже
  создаёт один общий Horizon service и подключает его кнопку/action handlers к
  обеим включённым платформам;
- одна общая bounded queue тяжёлых задач с независимо настраиваемыми workers, admission на
  пользователя, fan-out одинакового ключа, timeout/cancellation, подписанные
  compact actions и отдельный bounded delivery path с двумя workers и
  ограниченным admission для cache hits;
- атомарный ограниченный disk cache с очисткой при старте, периодически и после
  публикации; короткие hard-link leases сохраняют допущенный к отправке PNG при
  eviction, а брошенные staging/lease artifacts удаляются при старте;
- provider-neutral сферическая геометрия `10 deg`/8 азимутов с midpoint-шагом
  500 м и расчёты
  турбулентности, поперечного ветра, облаков, локального тумана наблюдателя,
  грубого HHL-рельефа, индекса и детерминированного качества данных;
- ICON-EU-only footprint checks и полный immutable acquisition `f000..f072`:
  точные почасовые surface/cloud/TKE/MH/visibility, линейная интерполяция
  исходных трёхчасовых pressure `U/V/T/Z` только внутри одного run и пакетный
  CDO extraction дедуплицированных ячеек с отдельным лимитом
  `horizon_analysis.cdo_workers`;
- контракт из 73 frames, заново вычисляющий HMNSP/TKE, `Cn2`, seeing, `tau0` и
  индекс каждого часа, а не интерполирующий нелинейные результаты, с той же
  полной калибровкой, что у Overall; эта калибровка входит и в cache identity;
- общая оценка, не зависящая от типа цели, сохраняет физические значения сиинга
  и `tau0`, но ограничивает их совместное снижение индекса величиной 25%;
- проверки current run до cache reuse/тяжёлой работы, в начале и конце
  acquisition, после расчёта/render и непосредственно перед каждой отправкой,
  включая cache hit; caption в момент отправки использует настроенный для
  ICON-EU `max_stale_age`;
- одна локализованная heatmap `3200x1400` «время × восемь направлений» для всех
  73 сроков, с фоном дня/сумерек/ночи, unavailable-ячейками, периодом run,
  актуальностью и компактным описанием ограничителя/качества данных;
- нижняя полоса качества каждой ячейки следует оценке срока прогноза:
  хорошие данные при `C_lead >= 0.85`, пригодные при
  `0.75 <= C_lead < 0.85` и ограниченные при `C_lead < 0.75`; невычислимый путь
  остаётся недоступным, а составная `Confidence` ниже `0.60` может только
  понизить категорию;
- unit tests затронутых пакетов для callback normalization, queue/cache,
  identity ряда, геометрии, local-ENU проекции ветра, dateline/high-latitude,
  границ provider, sparse/missing profiles и физических closures;
- команду `render-horizon` для реальной проверочной отрисовки по текущему циклу
  ICON-EU;
- геометрический эталон однородного пути, выведенный из реализованного
  сферического луча, а не из приближения молекулярной воздушной массы;
  физические значения сиинга и `tau0` вдоль наклонного луча не меняются, а
  опорные границы используют точное отношение путей в степени Фрида `3/5`.

## Production-изменение Overall

Аудит обезличенного исторического контрольного примера обнаружил, что
развёрнутый legacy HMNSP99-расчёт не разрешает PBL и даёт узкий ряд около
`0.70…0.77″`; smoothstep с прежней лучшей границей `0.7″` и condensate без
защиты от несогласованного `CLC` создают слишком много значений `10`.

В production развёрнута следующая схема:

- `surface-hourly-v17` публикует 17 single-level полей на каждый из 79 часов,
  включая ICON `MH`/ecCodes `mld` в метрах;
- `cloud-hourly-v4` публикует ровно 187 сообщений на каждый час:
  `CLC/P/T/QC/QI` на всех 27 выбранных model levels, `U/V` на непрерывных
  `58…74`, `TKE` на half levels `58…75` и отдельную `HHL`-геометрию;
- Masciadri `Cn²` интегрируется трапециями от поверхности до почасовой границы
  `h_PBL=clamp(ICON_MH,500,2000) m AGL`; HMNSP99 применяется только выше той
  же границы, а полный `J` даёт model-derived seeing на 500 нм;
- `tau0` рассчитывается из `integral(Cn²·|V|^(5/3)dz)`; отдельного повторного
  штрафа за направление нет, поскольку vector shear уже содержит разворот;
- физические seeing и `tau0` входят в ограниченную turbulence utility
  `f=0.75+0.25*q_turbulence`: они не veto для чистого универсального часа, а
  облачное пропускание и туман сохраняют более сильную роль преграды;
- приземный ветер штрафует мягко, максимум на 20%; роса исключена, возможный
  и высокий туман используют множители `0.75/0.10`;
- карта вычисляет массу каждого native слоя как
  `P_Pa/(287.05·T)·abs(HHL[k]−HHL[k+1])`, поэтому sparse levels не раздувают
  condensate path;
- unresolved-CLC guard зависит от яруса: low `0.45·C`, middle
  `0.55·0.45·C=0.2475·C`, high `0.18·0.45·C=0.081·C`; это консервативная
  инженерная неопределённость, не физическая opacity, а более сильный
  `QC/QI` optical-depth результат всегда выигрывает;
- карта применяет общий optical-depth kernel/guard policy на каждом native
  level, а Overall использует total-column `TQC/TQI` и random overlap
  `CLCL/CLCM/CLCH`; поэтому их числа не объявляются идентичными;
- point-cache schema поднята до `point-v6-native-cloud-mass-mh`, чтобы старые
  записи без `MH`, `T` и нативной толщины слоя не переиспользовались;
- version markers синхронизированы с новым контрактом:
  `seeing-hybrid-tke-mh-hmnsp99-v6`,
  `conditions-v7-phase-structure-coherence`, `render-v15-four-solar-bands` и
  `shared-render-v18-phase-structure-coherence`.

Server-side fixed-2-km расчёт двух сроков без подгонки
(`ground Cn² scale=1`) дал для исторического контрольного примера `2.221″` на `f042` и `3.644″` на
`f048`; ground layer содержал соответственно 88.36% и 94.43% `J`. После
подключения `MH=396 m` на обоих сроках расчёт без clamp дал
`1.9075″/2.5158″`, а production-minimum 500 м — `1.9145″/2.5478″`. Это
server-only регрессия причины ошибки, не наблюдательная калибровка. Полный
production sync `surface-hourly-v17`/`cloud-hourly-v4` для run `2026072106`
завершён, новый образ развёрнут, а live CLI-путь Telegram проверен на контрольном примере.

[научная методика и расчётная записка](scientific-method.ru.md).

Контроль старой cloud-physics версии дал: 22.07 09:00 UTC при `CLCT=72.8%`, `TQI=0.000015 kg/m²`, `τ=0.00105` вычисленное пропускание `99.90%`, Overall `9.98`; 22.07 02:00 при `CLCT=100%`, `τ=2.78` — `6.20%` и Overall `1.03`. Добавлен bounded performance layer: surface/wind/cloud извлекаются параллельно и объединяются в один point bundle, совпавшие miss объединяются, `gob.gz` кеш хранится для двух run × 512 ячеек, RAM LRU ограничен 512 ячейками/20 GiB, а семь PNG кешируются на 48 часов (до 256 комплектов). Production использует provider-versioned point cache; старые schema автоматически игнорируются. Каждая платформа использует шесть шардированных по peer workers и 15-минутный request timeout, чтобы первый full-native Global point extraction успел завершиться; ecCodes/CDO делят общий лимит восемь процессов. Каждая загрузка объекта DWD по-прежнему имеет ограниченный двухминутный HTTP timeout и три попытки, а scheduler не ограничен timeout пользовательского запроса. Временные cache staging старше часа и Docker-логи сверх `3 × 10 MiB` удаляются автоматически.
