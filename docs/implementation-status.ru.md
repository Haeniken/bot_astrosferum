Дата: 2026-08-14
Этап: Stage 3, live ICON → Telegram и VK; текущий быстрый «Горизонт» v12 использует прямой луч и статическую информационную линию рельефа Copernicus DEM GLO-30 по нативным ячейкам; контролируемый rollout астрокупола и анонимная эталонная визуализация только для чтения развёрнуты, production-v2/v33/v23 является текущим, а полный v28/v22 сохранён как измеренный baseline атмосферного пути

## Готово

- PostgreSQL 18.4 хранит пользователей, до 10 точек на пользователя и ограниченные 90 днями суточные агрегаты запросов;
- клавиатуры Telegram и VK поддерживают сохранение/выбор точек; администраторы платформ из `.env` получают общее число учётных записей и единый PNG по запросам обеих платформ за 30 дней;
- Light Pollution Atlas 2024 дополнен отдельным сравнением World Atlas 2015; обязательный GeoTIFF автоматически восстанавливается при старте;
- runtime использует официальный OSGeo GDAL 3.13.1 и ecCodes 2.45.0.
- имена полей поверхности нормализуются между версиями ecCodes (`VMAX_10M`/`max_i10fg`);
- админский график использует составные столбцы «успешно/с ошибкой» и календарные сутки MSK (UTC+3); меню точек имеют кнопку «Назад».

- Go `1.26.6`, `tzf v1.2.5`, `gonum/plot v0.17.0`;
- Telegram принимает native location, а VK — geo-вложение; обе платформы принимают `59.9386, 30.3141` и `/forecast 59.9386 30.3141`;
- оба тонких platform adapter зависят от общего обработчика `internal/app/bot` и не импортируют друг друга; VK Group Long Poll включается при старте, сообщения и geo приводятся к общему запросу, а тексты, клавиатуры, PNG-фото и документы без потери качества переводятся в вызовы VK API;
- Telegram и VK работают под независимыми перезапускающими supervisor, поэтому сбой API одной платформы не останавливает синхронизацию моделей и вторую платформу;
- обычные прогнозы имеют общий межплатформенный лимит расчётов и после занятия двух настроенных слотов сообщают место в очереди; «Горизонт» и астрокупол делят одну ограниченную directional FIFO и отдельно настраиваемую concurrency изолированного worker (`1` рекомендуется до измерений);
- VK photo/document upload проверяет handshake и делает не более двух повторов с паузами `1 с`/`2 с` и новым upload URL; это обрабатывает временные `405` или неполные ответы `pu.vk.ru` без бесконечных retry;
- между последовательными исходящими сообщениями одного VK-запроса действует минимальный интервал `250 мс` без общей блокировки; параллельные VK-запросы и отправка Telegram не менялись;
- `/start` и `/help` объясняют запрос и интерпретацию всех семи графиков;
- пользовательское сообщение показывает выбранную модель, run ID и возраст model run относительно настраиваемого `max_stale_age`; этот порог управляет только предупреждением `⚠️ stale run` и не удерживает данные в кеше. Run ID входит в ключи point/render cache, поэтому новый опубликованный run автоматически даёт cache miss;
- язык Telegram определяется по `User.language_code`: только `ru*` получает русский интерфейс, любой другой или отсутствующий код — английский; локализованы помощь, статусы, ошибки, кнопки, подписи, погодная таблица и все заголовки/оси/легенды PNG, а render-cache разделён по языку;
- VK пока использует русский по умолчанию, поскольку Group Long Poll не передаёт аналог Telegram `language_code`;
- timezone определяется offline по координатам и подписывается на каждом PNG;
- DWD discovery выбирает последний полный ICON-EU цикл `00/06/12/18` с доступным `+72 h`;
- координаты вне домена ICON-EU маршрутизируются на последний полный ICON Global `00/06/12/18` на полной native global grid; CDO использует официальную статическую геометрию DWD для выбора ближайшего native-узла без обрезки источника и без второй мировой raster-копии;
- ICON Global теперь синхронизирует тот же 79-часовой 27-уровневый контракт `CLC/P/T/QC/QI + нижние U/V/TKE + HHL`, что ICON-EU, используя эквивалентные по высоте model indices со сдвигом `+46`; DWD Global TKE заканчивается на `+48 ч`, поэтому до него bundle содержит 187 сообщений/час, затем 169, cloud map остаётся полной, а гибридный Overall заканчивается без экстраполяции отсутствующей турбулентности; прямой `VIS` также остаётся недоступен в DWD Global feed;
- atomic sync скачивает pressure-level `U/V/FI/T`, не сохраняет `.bz2`, проверяет каждый бандл через ecCodes и SHA-256;
- старый pressure-level run атомарно дополняется только отсутствующими `FI/T`; scheduler независимо публикует versioned hourly surface/cloud bundle, а ecCodes 2.45 `clwmr/QI` нормализуются во внутренние `qc/qi`;
- ICON-EU и ICON Global оставляют предыдущий полный `current` доступным, пока загружаются все компоненты нового run; `current` переключается одной атомарной symlink-операцией только после полной проверки;
- sync защищён exclusive lock; scheduler запускает проверку при старте, затем каждые 15 минут и хранит два последних run; пользовательский запрос ничего не скачивает, а читает последний полностью опубликованный набор;
- point extractor параллельно получает 25 вертикальных профилей из текущего manifest;
- независимый surface sync публикует 79 почасовых бандлов `f000…f078` с `T_2M`, `TD_2M`, `RELHUM_2M`, `CLCT/CLCL/CLCM/CLCH`, `TOT_PREC`, `U_10M`, `V_10M`, `VMAX_10M`, `PMSL`, `VIS`, `TQV` и точными столбовыми `TQC/TQI`; `PMSL` сохраняется только для погодного продукта и никогда не передаётся в SPECTRL2;
- обе платформы показывают 72 часа; туман берётся из прямого `VIS`, а карта облаков показывает эффективную преграду по высоте из `CLC+QC+QI` и фазовой оптической толщины;
- роса показывается только как подсказка о подготовке обогрева/бленды и не снижает seeing или практический score;
- pure-Go astronomy рассчитывает состояние Солнца/Луны, а также почасовые топоцентрические планировочные эфемериды и восходы/заходы Меркурия, Венеры, Марса, Юпитера, Сатурна, Урана, Нептуна и Плутона; регрессии событий Солнца/Луны остаются в пределах двух минут от эталона, а контроль всех тел по JPL Horizons `AIRLESS` укладывается в `0.15 градуса` при сохранении оговорки о планировочной точности;
- обе платформы отправляют одинаковые семь PNG; увеличенный график Overall
  `4320×1600` объединяет гибридный сиинг ICON TKE/MH + HMNSP99, `tau0`,
  эффективное облачное пропускание по `CLCT+TQC+TQI`, туман, мягкий приземный
  ветер и бинарный запрет по осадкам от настраиваемого порога обнаружения
  `R_1h >=0.05 mm`;
- один сохранённый кусочно-линейный профиль `Cn2` теперь даёт сиинг, `tau0`,
  `theta0`, эффективные высоту и скорость ветра турбулентности,
  `FracGL250/500/1000` для фиксированных высот, сиинг свободной атмосферы выше
  500 м, вертикальную полноту и геометрическую полноту момента `h^(5/3)`;
  совместимые поля динамического PBL явно
  отделены от похожих на MASS фиксированных долей. Overall отклоняет любую
  полноту ниже `90%` либо верх профиля ниже `15 км AGL`; `complete` требует
  `99%/99%` и не менее `18 км AGL`, а любое иное качество ставит `!`;
- график 2 показывает сохранённый индекс под точным пятицветным разложением
  Шепли величины `10-Overall`; составной столбец замыкается на 10, осадки
  обозначают явный запрет, а `!` — частичные данные, не вероятность;
- в астрономическую ночь на график 2 может накладываться отдельное кольцо
  эффективности Reference Johnson V вдоль геометрического зенита,
  усреднённого по ячейке сетки, для явно заданного режима слабого источника,
  фонового ограничения, ограничения сиингом и отсутствия адаптивной оптики.
  Контракт `reference-v-band-zenith-efficiency-v2` и атмосферная модель
  `reference-v-band-spectrl2-ks91-v3` используют давление/PWV/полную
  облачность ICON и AOD550/озон NASA GEOS-CF; KS91 задаёт лунный фон, а
  фотонно-взвешенная смесь PSF — эквивалентную по шуму площадь. Облака
  ослабляют источник, тогда как естественный и лунный фон чистого воздуха
  удерживается как консервативный нижний предел, поэтому модельный облачный
  отклик приблизительно равен `T²`; отсутствие яркости рассеянного облаками
  неба явно указано как ограничение. Непрозрачный столб не содержит
  `ExtinctionMag` и ставит `OpaqueTransmission`; отсутствие сиинга/состава даёт
  partial, а высокий сигнал `FogHeuristic` или осадки делают результат эксплуатационно
  недоступным и убирают маркер. Искусственная засветка исключена, а Reference
  V не умножается на универсальный Overall;
- Reference V получает фактическое давление на поверхности модели из нижних
  доступных нативных `P/T` того же часа и `HHL` полного уровня/поверхности по
  формуле `p_s=p_l exp[g_0(z_l-z_s)/(R_d T_l)]`; маркер происхождения —
  `icon-lowest-model-level-p-hydrostatic-to-hhl-surface-v1`. При отсутствии
  входов или промежутке переноса больше `1 км` результат становится частичным,
  без подстановки `PMSL` или стандартной атмосферы;
- ограниченный клиент GEOS-CF OPeNDAP записывает независимые цикл и
  актуальность, ограничивает время, размер ответа, кэш и совпадающие запросы и
  обрабатывает сбой без отказа ICON: отсутствующий или устаревший состав лишь
  убирает Reference V; сетевой тайм-аут равен `60 с`, операция корневого
  контекста сервиса ограничена `65 с` и отменяется при остановке, а обычный
  пользовательский ответ присоединяется не более чем на `5 с`. Одинаковые
  наборы уровней объединяются, разные загрузки ограничены
  `ASTRO_FORECAST_CONCURRENCY`, а заполненный ограничитель не запускает новый
  необязательный запрос;
- функции для конкретной цели реализуют оптическую воздушную массу
  Kasten-Young, масштабирование атмосферной FWHM по
  `X^(3/5) lambda^(-1/5)` и явно ограниченное гауссовым случаем квадратурное
  сложение качества изображения; в Overall по одним координатам эти величины
  незаметно не добавляются;
- текстовый блок получает точечную оценку засветки из Light Pollution Atlas 2024: билинейные LPI/SQM на сетке около `30″` и честно помеченный ориентир Бортля; засветка не входит в Overall Index;
- значения в heatmap увеличены до 8 pt и сделаны полужирными, оси и bar labels также увеличены;
- старый wind-only index сохранён отдельным диагностическим графиком; direction delta равен `0°` при ветре `<2 m/s`, а `NaN` означает только отсутствие данных;
- контейнер работает от `1000:1000`, с read-only root filesystem и bind mounts бота/worker внутри `/opt/docker/bot-astrosferum`;
- `go test ./...`, `go vet ./...` и `doctor` проходят.

## Анализ «Горизонт» — реализован

Опциональный анализ «Горизонт» является существующей функцией приложения и
управляется параметром `ASTRO_HORIZON_ANALYSIS_ENABLED`. Он намеренно доступен только
после обычного прогноза ICON-EU и охватывает полный неизменяемый интервал
`f001..f072`. Для ICON Global нет ни кнопки, ни запускаемой задачи «Горизонт».
Реализация включает:

- environment/configuration switch с валидацией и disabled-путём, которому не
  требуются operational limits Horizon;
- небольшой общий versioned action router и нормализованные callback events
  Telegram/VK; в platform adapters нет формул Horizon; composition root уже
  создаёт один общий Horizon service и подключает его кнопку/action handlers к
  обеим включённым платформам;
- одна общая bounded queue тяжёлых задач с настроенным directional-лимитом
  активных слотов, admission на
  пользователя, fan-out одинакового ключа, timeout/cancellation, подписанные
  compact actions и отдельный bounded delivery path с двумя workers и
  ограниченным admission для cache hits;
- атомарный ограниченный disk cache с очисткой при старте, периодически и после
  публикации; короткие hard-link leases сохраняют допущенный к отправке PNG при
  eviction, а брошенные staging/lease artifacts удаляются при старте;
- восемь азимутов со сферическим прямым лучом, запущенным на
  геометрической высоте `10°` и разбитым на 500-метровые отрезки наземного пути до
  22,3 км MSL; поле Ciddor и событийный луч Дормана--Принса остаются только в
  астрокуполе; готовые сиинг, `tau0`, облачная преграда, индекс и качество не интерполируются;
- ICON-EU-only footprint checks и immutable acquisition `f001..f072`:
  точные почасовые surface/cloud/TKE/MH/visibility, линейная интерполяция
  исходных трёхчасовых pressure `U/V/T/Z` только внутри одного run и пакетный
  CDO extraction дедуплицированных ячеек с общим лимитом
  `horizon_analysis.cdo_workers`; Horizon строит один `gennn`-план на запрос и
  переиспользует read-only weights во всех `remap`;
- контракт из 72 frames, заново вычисляющий HMNSP/TKE, `Cn2`, seeing, `tau0` и
  индекс каждого часа, а не интерполирующий нелинейные результаты, с той же
  полной калибровкой, что у Overall; эта калибровка входит и в cache identity;
- общая оценка, не зависящая от типа цели, сохраняет физические значения сиинга
  и `tau0`, но ограничивает их совместное снижение индекса величиной 25%;
- проверки current run до cache reuse/тяжёлой работы, в начале и конце
  acquisition, после расчёта/render и непосредственно перед каждой отправкой,
  включая cache hit; caption в момент отправки использует настроенный для
  ICON-EU `max_stale_age`;
- одна локализованная heatmap `3200x1400` «время × восемь направлений» для всех
  72 сроков, с фоном дня/сумерек/ночи, unavailable-ячейками, периодом run,
  актуальностью и компактным описанием ограничителя/качества данных;
- нижняя полоса качества каждой ячейки использует детерминированную эвристику
  качества по сроку прогноза:
  хорошие данные при `C_lead >= 0.85`, пригодные при
  `0.75 <= C_lead < 0.85` и ограниченные при `C_lead < 0.75`; невычислимый путь
  остаётся недоступным, а составная эвристика качества данных ниже `0.60` может только
  понизить категорию;
- unit tests затронутых пакетов для callback normalization, queue/cache,
  identity ряда, геометрии, local-ENU проекции ветра, dateline/high-latitude,
  границ provider, sparse/missing profiles и физических closures;
- команду `render-horizon` для реальной проверочной отрисовки по текущему циклу
  ICON-EU;
- геометрический эталон однородного пути, выведенный из реализованного
  сферического луча, а не из приближения молекулярной воздушной массы;
  физические значения сиинга и `tau0` вдоль наклонного луча не меняются, а
  опорные границы используют точное отношение путей в степени Фрида `3/5`.

`123,541 с`. Во время активного извлечения данных «Горизонтом» обычный прогноз
завершился за `10,074 с`, что ниже контрольной границы `14,193 с`.
Проверка Global построила семь графиков за `174,586 с`; команда
«Горизонт» для той же точки завершилась ошибкой и не создала PNG.
После того исторического развёртывания также прошли проверки `doctor`, готовности PostgreSQL,
актуальности циклов, логов старта, перезапусков/OOM, очистки ограниченного кэша и
отсутствия секретов/координат в логах.

При каждом развёртывании проверяются тесты репозитория, детектор гонок,
статический анализ, линтер и сборка, реальный расчёт по текущему циклу ICON-EU,
явное отсутствие кнопки и задачи для ICON Global, состояние сервисов и логи
старта, обычный прогноз и «Горизонт», а также задержка обычного прогноза во
время параллельного расчёта «Горизонт». При провале обязательной проверки
выполняется откат либо отправляется отчёт об ошибке вместо сообщения об успехе.

## Астрокупол — контролируемый rollout и публичный эталон развёрнуты, полный прогон измерен

Полный web-продукт только для ICON-EU развёрнут с контролируемым доступом к расчётам как один
асинхронный набор из не более чем 72 последовательных нативных почасовых сроков от явной границы расчёта 10° до единственного
зенитного узла без азимута. В коде готовы:

- production-сетка `production-v2`: восемь колец
  `10/20/30/40/50/60/70/80°`, по 16 азимутов, и один зенит — 129 узлов/срок,
  72 кадра и 9 288 узло-часов. `sparse-storage-v1` с 97 узлами остаётся
  дисковым fallback, а `dense-v1` с 353 узлами — только историческим
  legacy/reference-контрактом; канонический порядок, descriptors/digests,
  сферические ячейки Вороного и строгий browser-contract версионированы;
- прямая геометрия на сфере ICON и полная влажная рефракция Ciddor с
  `dormand-prince-5-4-event-v3`: production согласует два прямых прохода, а
  дополнительный обратный проход выполняется только reference-режимом для
  регрессии, калибровки и release verification;
- строгий контракт `astrodome-science-kernel-v33-glo30-informational-skyline` /
  `astrodome-science-path-v23`: локализация физических и горизонтальных корней
  до 0,2 мм, обнаружение сближения разных корней в пределах 0,4 мм с отказом,
  запас стороны 0,5 мм, доказательный масштаб 0,2 мм, неизменный
  1-миллиметровый порог вычисления положения и координат, ограниченный результат
  средней точки на `0,002366025404… м` и ниже только для трёх безопасных проб
  одного раздела, отсутствие экстраполяционного Q5/Q3, а
  независимые GL2/GL1, GL3/GL2 и GL5/GL3 применяются ниже соответствующих
  верхних границ `0,004436491673…`, `0,010658690662…` и
  `0,117032584345… м`;
  для вычисления точки плотного полинома применяются покомпонентные суммы
  модулей мономов с проверенной оболочкой `gamma128` и округлённым наружу
  евклидовым объединением, а более общие границы производной и ускорения по
  Бернштейну сохраняют `gamma1024`;
  обычные строгие пределы равны `0,001000000000001… м` для двух физических
  концов без доказательства короткой панели,
  `0,0005000000000005… м` для одного физического конца и `0,01 м` для двух
  численных; ветка с доказательством использует свой сертифицированный открытый
  безопасный интервал. Сумма длин панелей средней точки и длина объединения
  допущенных краевых полос ограничены 1 м; принятый результат получает
  `limited`, нулевой признак сходимости квадратуры и
  `short_path_approximation`. Только побитово идентичные координаты одновременных событий
  образуют одну геометрическую точку разбиения с сохранением упорядоченного
  объединения идентификаторов; побитово различные координаты не объединяются.
  Обе оставшиеся пары правил имеют фиксированные положительные веса и берут
  значения только внутри сертифицированной панели. Значения за запасами у
  концов не используются для восстановления пропущенного интервала.
  Production использует накопленную встроенную оценку выбранной пары
  правил; независимый полный повтор с половинными допусками и одноразовым
  делением исходных панелей включается только в reference-режиме. Обе оценки
  остаются инженерными, а не строгой оболочкой;
- односторонние сертификаты производной для пропущенного участка у конца
  ограничены HHL, полными уровнями, облачными ярусами и исходными билинейными
  предикатами PBL. Их полная округлённая наружу односторонняя оболочка остатка
  принимает участок только при исключении нуля; это охватывает ограниченное
  движение как от нуля, так и к нему без вычисления в неоднозначно
  принадлежащей ячейке конечной точке. Если оба доказательства не исключили
  корень, путь v23 учитывает только эту пропущенную краевую полосу в
  ограниченном метровом бюджете; все внутренние точки WMO по-прежнему обязаны
  быть сертифицированы до квадратуры, а любое несовпадение разбиения в ядре
  приводит к отказу;
- точные вычислительные ошибки для каждой пробы: 1 мм является только порогом
  отказа; ECEF-предикаты используют фактическую границу плотного положения,
  билинейные поля — собственную координатную неопределённость, физические
  остатки высоты складывают фактические члены луча/операндов, а 200 гПа
  распространяет координатные и арифметические интервалы исходных H/P;
- сжимающий оператор (contractor) монотонных корней path v22 сохраняет исходное
  доказательство
  существования и единственности, затем пересекает отдельную скобку корня с
  округлёнными наружу образами защищённого интервального метода Ньютона в
  концах и середине. После недостаточного сокращения в середине выполняются
  парные внецентровые пробы по обе стороны центрального окна; интервал остатка,
  содержащий ноль, не получает знак по номинальному значению, а непреодолимый
  информационный предел по-прежнему приводит к отказу. Для приёмки оба радиуса
  корня всё так же не должны превышать 0,2 мм; порог разных корней 0,4 мм и
  запас стороны 0,5 мм не изменены;
- смешанные PBL-ячейки разделяются по строго изолированным исходным решениям
  `MH-500 м` и `MH-2000 м` до расчёта гладкой ветви clamp; совпадающая верхняя
  граница `HSURF+2000 м`/нижних облаков регистрируется только один раз;
- четырёхмерное восстановление исходных полей ICON-EU. Пространственная и
  временная интерполяция выполняется до всех нелинейных формул; готовые сиинг,
  `tau0`, пропускание облаков, Overall и качество не интерполируются. Давление
  на исходных полных уровнях должно строго возрастать от верха модели к
  поверхности, исходное `PS` обязано превышать давление нижнего полного
  уровня, а восстановленное поле должно удовлетворять `dP/dz < 0`; нарушение
  приводит к отказу до рефракции и научного интегрирования;
- сертифицированные верхние оболочки CLC по четырём исходным столбцам шаблона,
  концам нативной временной скобки и точной активной соседней паре полных
  уровней (либо одному уровню продолжения сверху или снизу). Выпуклое
  восстановление и направленный наружу допуск binary64 ограничивают каждый
  атомарный интервал; идентификатор вертикальной опоры входит в сигнатуру
  разбиения и ключ кеша, а отсутствие сертификата поставщика или смена в
  пробах приводит к отказу. Максимум по всему ярусу или столбцу не берётся;
- раздельные номинальное и консервативное пропускания облаков. Каждый точный
  блок «ячейка/ярус» накапливает собственную жидкую/ледяную оптическую толщину
  и встроенную ошибку; консервативное значение использует оболочку CLC и
  `tau_block + error_block` и только оно входит в направленный Overall;
- совместное интегрирование по лучу `Cn2`, взвешенного поперечным ветром
  `Cn2`, наклонного водяного пара и фазового облачного поглощения, после чего
  применяется общий ограниченный Overall и veto осадков;
- одна настроенная калибровка Overall/облаков для обычного Overall, Horizon и
  Astrodome. Схема расчётного запроса v5 и каждый текущий dataset сохраняют
  SHA-256 полной проверенной калибровки Astrodome; изменение настроек
  конструктивно меняет ключ кеша, а несовпадение bot/worker приводит к отказу;
- полные dome manifest/acquisition/volume contracts, identity и leases run,
  возобновляемое дополнение совпадающего неизменяемого base-run, admission по
  хранилищу и атомарная публикация сжатого результата;
- параллельная предзагрузка footprint: проверка исходной GRIB-сетки, CDO
  `gennn`-цели только с точными нативными индексами, digest плана, общие
  read-only weights и до восьми `remap` subprocesses для нативных сроков.
  Сгенерированный SCRIP-файл обязан содержать ровно одну связь на цель,
  ожидаемые адреса исходной и целевой ячеек и вес, чьё binary64-значение точно
  равно единице. Каждый GRIB, к которому применяются веса, должен иметь ту же
  геометрию регулярной сетки и тот же порядок сканирования, что доказанный
  HHL-источник. Обычный
  ICON-EU прогноз остаётся на `grib_get -l`, point cache, RAM LRU и
  single-flight и не зависит от этого preload;
- одна ограниченная FIFO для «Горизонта» и астрокупола с
  `ASTRO_DIRECTIONAL_CONCURRENCY` активными тяжёлыми задачами (`1` рекомендуется
  до измерений) и изолированный directional worker, который читает модели
  только для чтения; process-shared context-aware slot leases также ограничивают
  случайные дополнительные реплики worker и операторский путь `render-horizon`;
- в отдельном частном `site-astrosferum` тонкий web-процесс с Telegram OpenID Connect, серверными сессиями,
  CSRF/Origin-check, least-privilege чтением сохранённых точек, ownership задач,
  асинхронными job/status/dataset API и такой же проверкой допуска в bot;
- локализованные публичные страницы `/en` и `/ru`, личный кабинет и отдельные
  инструменты обычного прогноза, «Горизонта» и астрокупола; вход через Telegram
  находится на главной, а весь сайт пока закрыт одновременно `noindex` и
  `robots.txt: Disallow /`;
- owner-scoped web-задачи обычного прогноза и «Горизонта» переиспользуют
  существующую очередь прогноза, render/Horizon cache, калибровку, общую
  directional FIFO, статистику и подготовленные научные значения без
  дублирования расчёта; бот публикует JSON `forecast-interactive-v6-observing-ephemerides` и
  `horizon-interactive-v7-glo30-informational-skyline` в ограниченном хранилище результата с проверкой
  владельца и TTL 96 часов, а сайт опрашивает статус и строит интерактивные
  графики без отправки сообщения в Telegram или VK;
- контракт обычных интерактивных графиков сохраняет раздельные нативные шкалы:
  одну точную почасовую ось погоды/облаков, её возможно более узкое точное
  подмножество Overall и независимую трёхчасовую ось pressure-level diagnostics
  без ресемплинга между ними; Overall никогда не выходит за границы поддержки
  pressure-level профиля;
  аддитивные пункты штрафов Overall сериализует Go, браузер только рисует их.
  Payload закрепляет `overall-astronomy-index-v2-fog-heuristic-availability`,
  `effective-cloud-obstruction-v1` и `overall_calibration_sha256`; при
  website-only cache miss PNG не растеризуется. Кроме того, он содержит десять
  точных канонических почасовых топоцентрических траекторий версии
  `celestial-observing-ephemerides-jpl-meeus-wgs84-h0-v4`; интерполяция по кратчайшей дуге
  применяется только к пунктирной геометрии отображения и не изменяет
  выбранный час либо метеоданные. Тот же контракт передаёт закреплённую
  исчерпывающую почасовую шкалу модельного расстояния, целое среднее значение
  близости за прогноз, значение выбранного часа с двумя знаками после запятой,
  знаковую радиальную скорость, угловой диаметр, фазу, освещённую долю,
  видимую величину V с явным статусом области модели, элонгацию, суточную
  кульминацию, сезон Марса и угол раскрытия колец Сатурна; ни одна из этих
  диагностик не изменяет Overall. Значения V Марса/Плутона явно помечены как
  планировочные приближения, а не значения опубликованной области модели.
  Астрокупол дополнительно содержит строгий версионированный слой Полярной
  звезды и фиксированные координаты SynScan
  ICRS/J2000. Отдельная диагностика Johnson-V показывает provenance NASA GEOS-CF при
  наличии состава атмосферы и не становится скрытым штрафом Overall;
- интерактивный payload «Горизонта» закрепляет точный артефакт кеша, HHL-высоту
  поверхности наблюдателя, provider/run/grid ICON-EU, версию научного расчёта,
  канонический digest калибровки Overall и нативную часовую ось `f001..f072`;
  непрерывные рассчитанные на сервере интервалы фаз Солнца покрывают
  `f001−30 мин .. f072+30 мин`, а worker до публикации обязан подтвердить
  закреплённый координатором ключ научного кеша;
  канонические unavailable-ячейки с главным ограничителем рельефа остаются
  видимыми и не приводят к отклонению всего результата;
- общие сохранённые точки можно выбирать, создавать и удалять на сайте в
  пределах существующего лимита десять; прогноз также принимает проверенные
  временные координаты, введённые напрямую, полученные по явному нажатию через
  геолокацию браузера либо выбранные на встроенной локальной карте;
- пользовательская настройка языка web-интерфейса `ru`/`en` в PostgreSQL,
  синхронизируемая между активными сессиями при сохранении явных URL локалей;
- входа и привязки VK ID пока нет: настроенный токен сообщества VK не является
  учётными данными приложения VK ID, поэтому небезопасная имитация отсутствует;
- gzip-архивы визуализаций с обычным TTL 96 часов и одна явная бессрочная
  запись `admin_fixture`, доступная только для чтения неавторизованным
  посетителям и каждому настроенному администратору Telegram, но не
  авторизованным пользователям без прав администратора. Фикстура и декодер сохранённых результатов принимают только
  v33/v23 с поддерживаемым закреплённым профилем; production web-output —
  `production-v2`. Старый payload отклоняется, пока успешный расчёт
  текущего контракта для тех же координат не заменит
  общую фикстуру, когда точное перекрёстное умножение целых чисел доказывает
  меньшую или равную долю `unavailable / total`; только строго худший результат
  её не заменяет;
- не зависящее от внешних библиотек представление изнутри купола WebGL2,
  fallback Canvas 2D и доступная таблица, фиксированные количественные легенды,
  keyboard/touch и строгая fail-closed проверка dataset; звёздный слой остаётся
  за сеткой, не содержащий данных контекст показывает обычную подпись `0°` без отдельной
  линии горизонта, сумеречное небо ниже расчётной границы `10°` и декоративный рельеф;
  `0°` и `10°` оформлены как обычные высотные ориентиры, один инспектор
  выбранной ячейки виден и в обычном, и в полноэкранном layout, та же почасовая шкала остаётся
  интерактивной в полноэкранном режиме без дублирования выбранного срока и автоматически
  появляется из нижней зоны по указателю или клавиатурному фокусу, восемь запрошенных полей имеют
  пояснения `ru`/`en`, а кнопки представления и полноэкранного режима не перекрывают компас;
- принадлежащие боту изолированный worker и внутренний API; Compose
  сайта и nginx-шаблоны закреплённого TLS живут в `site-astrosferum` и
  разворачиваются в `/opt/docker/site-astrosferum`.

Rollout-переключатель реализован как управление доступом, а не выключение
worker: `ASTRO_ASTRODOME_ENABLED=true` разрешает всех авторизованных через
Telegram OIDC; `false` оставляет доступ только `ASTRO_TELEGRAM_ADMIN_IDS`;
`false` с пустым списком запрещает всем. Правило проверяется и web, и bot.
Неавторизованный посетитель может только читать постоянную фикстуру и не
получает доступ к точкам или операциям с задачами. Режим доступа не принуждает
sparse-сетку: оба расчётных режима используют профиль, выбранный `DiskBudget`.
Полный dense-volume отображается в `production-v2`, а
`sparse-storage-v1` применяется только при объявленном дисковом ограничении.

На неизменяемом цикле ICON-EU `2026080812` (SHA-256 манифеста
`85d94a87e24a5eba4775baf4e46a4151c8c30021f51af6c54299cdbbabc5482e`)
исторический baseline production-v2/v28/v22 охватил все 72 нативных срока
`f002..f073` и все 129 узлов, то есть 9 288 узло-часов. Он завершился за
33 мин 14 с после предзагрузки 2 863 исходных колонок за 357,118 с; пиковая
память контейнера составила 15 127 642 112 байт. Доступны 9 284 узла. Ровно
четыре узла (f005/56, f007/9, f025/40 и f026/40) честно закрылись с

## Production-изменение Overall

Аудит обезличенного исторического контрольного примера обнаружил, что
развёрнутый legacy HMNSP99-расчёт не разрешает PBL и даёт узкий ряд около
`0.70…0.77″`; smoothstep с прежней лучшей границей `0.7″` и condensate без
защиты от несогласованного `CLC` создают слишком много значений `10`.

В production развёрнута следующая схема:

- `surface-hourly-v17` публикует 17 single-level полей на каждый из 79 часов,
  включая ICON `MH`/ecCodes `mld` в метрах;
- `cloud-hourly-v4` публикует ровно 187 сообщений на каждый час:
  `CLC/P/T/QC/QI` на всех 27 выбранных model levels, `U/V` на непрерывных
  `58…74`, `TKE` на half levels `58…75` и отдельную `HHL`-геометрию;
- Masciadri `Cn²` интегрируется трапециями от поверхности до почасовой границы
  `h_PBL=clamp(ICON_MH,500,2000) m AGL`; HMNSP99 применяется только выше той
  же границы, а полный `J` даёт model-derived seeing на 500 нм;
- `tau0` рассчитывается из `integral(Cn²·|V|^(5/3)dz)`; отдельного повторного
  штрафа за направление нет, поскольку vector shear уже содержит разворот;
- каждая трапеция `J_V` усредняет концевые значения `Cn²·|V|^(5/3)`, а не
  возводит среднюю скорость интервала в степень `5/3`; это исключает
  занижение по неравенству Йенсена на градиентах ветра;
- физические seeing и `tau0` входят в ограниченную turbulence utility
  `f=0.75+0.25*q_turbulence`: они не veto для чистого универсального часа, а
  облачное пропускание и туман сохраняют более сильную роль преграды;
- приземный ветер штрафует мягко, максимум на 20%; роса исключена, возможный
  и возможный/высокий сигналы `FogHeuristic` используют множители `0.75/0.10`;
- карта вычисляет массу каждого native слоя как
  `P_Pa/(287.05·T)·abs(HHL[k]−HHL[k+1])`, поэтому sparse levels не раздувают
  condensate path;
- unresolved-CLC guard зависит от яруса: low `0.45·C`, middle
  `0.55·0.45·C=0.2475·C`, high `0.18·0.45·C=0.081·C`; это консервативная
  инженерная неопределённость, не физическая opacity, а более сильный
  `QC/QI` optical-depth результат всегда выигрывает;
- карта применяет общий optical-depth kernel/guard policy на каждом native
  level, а Overall использует total-column `TQC/TQI` и random overlap
  `CLCL/CLCM/CLCH`; поэтому их числа не объявляются идентичными;
- схема point-cache ICON-EU поднята до `point-v7-explicit-heuristics`, а ICON
  Global использует `point-v3-explicit-heuristics`; bundles с прежними
  экспортируемыми именами полей Gob, как и записи без `MH`, `T` и нативной
  толщины слоя, не могут переиспользоваться как текущие данные;
- version markers синхронизированы с новым контрактом:
  `seeing-hybrid-tke-mh-hmnsp99-v7`,
  `conditions-v8-precip-veto-penalty-decomposition`,
  `render-v18-celestial-distance` и
  `shared-render-v24-explicit-heuristics`; Reference V
  независимо входит в ключ как `reference-v-band-zenith-efficiency-v2`,
  `reference-v-band-spectrl2-ks91-v3` и
  `reference-v-band-benchmark-v1`.

Server-side fixed-2-km расчёт двух сроков без подгонки
(`ground Cn² scale=1`) дал для исторического контрольного примера `2.221″` на `f042` и `3.644″` на
`f048`; ground layer содержал соответственно 88.36% и 94.43% `J`. После
подключения `MH=396 m` на обоих сроках расчёт без clamp дал
`1.9075″/2.5158″`, а production-minimum 500 м — `1.9145″/2.5478″`. Это
server-only регрессия причины ошибки, не наблюдательная калибровка. Полный
production sync `surface-hourly-v17`/`cloud-hourly-v4` для run `2026072106`
завершён, новый образ развёрнут, а live CLI-путь Telegram проверен на контрольном примере.
Подробности:
[научная методика и расчётная записка](scientific-method.ru.md).
