# Научный статус и воспроизводимость

## Статус

`bot_astrosferum` — научно-техническое исследовательское ПО: оно получает данные численного прогноза погоды, применяет документированные физические и инженерные модели и строит воспроизводимые диагностические материалы для наблюдательной астрономии и астрофотографии.

Это не рецензированная научная публикация, не откалиброванный инструмент обсерватории и не замена локальным измерениям. Seeing и Overall Astronomy Index являются модельными оценками. Для утверждений об абсолютной точности нужна проверка по DIMM, MASS, SCIDAR, площадочным SQM, all-sky камерам и структурированным журналам наблюдений.

## Исследовательский вопрос и результаты

Практический вопрос системы: насколько конкретные координаты и час подходят для астрономических наблюдений с учётом модельной турбулентности, ветра, облачной преграды, тумана, дневного света и астрономических событий?

Ответ разделён на проверяемые компоненты:

- погода и облачность по ярусам;
- эффективная облачная преграда по нативным уровням модели;
- скорость ветра, векторный сдвиг и изменение направления;
- ветровой и общий индексы пригодности;
- события Солнца, Луны, Юпитера и Сатурна;
- точечный контекст засветки, не смешанный с почасовым индексом.

## Происхождение данных

Каждое изображение указывает provider, продукт, run модели, сетку, часовую зону, версию алгоритма и renderer. Основной метеорологический источник — открытые данные DWD ICON-EU. Для засветки используется явно выбранный оператором год Light Pollution Atlas и отдельное сравнение с World Atlas 2015.

Модельные run и атласы намеренно не хранятся в Git: это большие восстанавливаемые данные внешних источников. Runtime manifest и версионированные ключи кэша не позволяют смешать несовместимые схемы.

Формулы, коэффициенты, допущения и ссылки на источники находятся в документах:

Общий индекс объединяет нативные термодинамику и турбулентность ICON в пограничном слое, HMNSP99 в свободной атмосфере, wind-weighted coherence time, оптическую толщину облаков с учётом фазы, guard неразрешённой облачности по ярусам, туман и мягкий штраф за приземный ветер. Роса и засветка индекс не уменьшают.

## Воспроизводимость

Для воспроизведения результата нужно зафиксировать:

1. revision или release tag исходного кода;
2. `config.yaml` без секретов и все `ASTRO_OVERALL_*` overrides;
3. ICON run ID и версии manifest;
4. координаты, найденную IANA timezone и интервал прогноза;
5. версии алгоритма и renderer, напечатанные на изображениях.

После этого нужно получить тот же upstream run, выполнить `sync-icon-eu` и `render-point`. Численный pipeline детерминирован при одинаковых входах и конфигурации; время создания файлов и доступность upstream относятся к эксплуатационным метаданным.

## Протокол валидации

- Unit-тесты проверяют parsing, единицы, выбор узла сетки, optical-depth kernels, интегрирование турбулентности, идентичность кэша и retention.
- Регрессии эфемерид используют публичные примеры Санкт-Петербурга и Москвы; эталон Солнца и Луны для Москвы получен из USNO one-day service.
- Synthetic fixtures проверяют renderer и никогда не попадают в пользовательский forecast path.
- Production smoke test проверяет полный manifest и все семь PNG.
- До наблюдательной проверки нельзя заявлять измеренную или откалиброванную для площадки точность.

Будущий calibration dataset должен содержать время, инструмент или метод наблюдения, неопределённость, высоту площадки и метеоконтекст. Площадки калибровки и проверки следует разделять, чтобы не переобучить коэффициенты на одну местность.

## Неопределённость и корректная интерпретация

- ICON-EU — сеточная прогнозная модель, а не точечный датчик.
- Подсеточная облачность, рельеф, локальные источники тепла, аэрозоль, dome seeing и конфигурация телескопа могут определять фактический результат.
- Восходы и заходы планет служат для планирования; для требовательной работы нужна высокоточная эфемерида.
- Бортль — приближённый ориентир из модельной яркости зенита, а не визуальная классификация на площадке.
- Индексы `1…10` ранжируют модельные условия; это не шкала Пикеринга и не наблюдательный seeing.

Публичные примеры содержат только Санкт-Петербург и Москву. Идентификаторы пользователей, сохранённые точки, токены и production credentials являются runtime-данными и не должны попадать в исследовательские материалы или GitHub issues.
