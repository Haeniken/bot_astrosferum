# bot-astrosferum: KISS-архитектура

Статус: реализованный MVP, архитектурная ревизия 0.4; data contract
`surface-hourly-v17`/`cloud-hourly-v4` работает в production. Опциональное
расширение «Горизонт» для ICON-EU реализовано как функция приложения,
управляемая конфигурацией. Расчётчик астрокупола и аутентифицированный
внутренний API кабинета развёрнуты здесь; публичное приложение принадлежит отдельному
частному репозиторию `site-astrosferum`. Текущий записывающий контракт —
`astrodome-science-kernel-v29`/`astrodome-science-path-v23`; полный v28/v22
остаётся предшествующим измеренным baseline; до
публичного rollout остаются повторные холодные/тёплые ресурсные и
наблюдательные проверки.
Дата проверки внешних источников: 2026-07-28; последняя ревизия: 2026-08-11
Среда развёртывания: управляемый оператором сервер
Каталог развёртывания: `/opt/docker/bot-astrosferum`

## 1. Решение в одном абзаце

Обычный продукт остаётся одним Go-процессом `bot_astrosferum`: он обслуживает
Telegram и VK, владеет PostgreSQL и публикацией модели, рассчитывает прогноз и строит PNG.
Единственная дополнительная граница изоляции научного runtime — тяжёлый
`directional_worker`, общий с «Горизонтом». Независимое приложение
[`site-astrosferum`](https://github.com/Haeniken/site-astrosferum) может
вызывать аутентифицированный внутренний API кабинета и использовать ботовую БД
через роль с минимальными правами; бот не импортирует и не вызывает сайт. Второго
загрузчика или реализации формул нет. Весь runtime бота остаётся в
`/opt/docker/bot-astrosferum` и продолжает работать без сайта.

### PostgreSQL, точки и статистика

PostgreSQL 18 работает внутренним Compose-сервисом с bind-volume `./data/postgres`. Приложение применяет идемпотентную схему при старте. Хранятся числовые ключи пользователей с раздельным пространством платформ, до 10 именованных координат на пользователя и одна агрегированная строка числа прогнозов на пользователя в сутки. Администраторы Telegram и VK задаются независимо через `ASTRO_TELEGRAM_ADMIN_IDS` и `ASTRO_VK_ADMIN_IDS`, но получают одну и ту же общую статистику по обеим платформам: суммарное число платформенных учётных записей и единый PNG-график запросов за 30 дней. Один человек в Telegram и VK считается двумя учётными записями, поскольку бот не связывает внешние идентичности.

Суточные агрегаты старше 90 дней очищаются при старте и раз в сутки; незавершённые диалоги сохранения точек живут не более двух часов.

### Атласы засветки

Основная строка использует Light Pollution Atlas 2024: нужные тайлы 30″ загружаются лениво и атомарно. Отдельная сравнительная строка использует World Atlas 2015 Falchi/GFZ. При старте обязательный GeoTIFF проверяется, а при отсутствии официальный ZIP скачивается, безопасно извлекается и удаляется. Засветка в Overall Astronomy Index не входит.

Runtime закреплён на официальном образе OSGeo GDAL 3.13.1. Координатная выборка World Atlas выполняется билинейно по окну 2×2 исходного GeoTIFF.

## 2. Главные архитектурные решения

| Область | Решение для MVP | Причина |
|---|---|---|
| Исполнение | `bot_astrosferum` и один directional worker в этом модуле; сайт — отдельный частный репозиторий и image | Одна научная реализация, однонаправленная зависимость сайта и явная изоляция отказов |
| Toolchain | Go `1.26.5`, закреплён в `go.mod` и Docker builder | Воспроизводимая актуальная сборка |
| Runtime | Основное приложение и опциональный directional-контейнер; сайт разворачивается отдельно | Обычный прогноз не зависит от отказа полного купола или сайта |
| Telegram | Bot API long polling | Не нужен ingress и webhook |
| VK | Bots Long Poll API | Не нужен публичный callback endpoint |
| Планировщик | Встроен в `bot_astrosferum serve` | Не нужен cron-контейнер или host cron |
| Ручные операции | Подкоманды `sync`, `doctor`, `render-sample` и render для точки/Horizon | Те же код и образ, что в production; `render-horizon` пока служит проверкой до развёртывания |
| GRIB2 | ecCodes для обычного extraction; CDO для точек ICON Global, ICON-EU Horizon batches и параллельной предзагрузки астрокупола | Без собственного GRIB-декодера и промежуточного GRIB на каждую точку; повторные пространственные поиски исключаются переиспользуемыми весами |
| Приоритетная модель внутри европейского домена | DWD ICON-EU | Открытая сетка ~7 км и полный набор surface/model-level полей |
| Модель вне европейского домена | DWD ICON Global | Стабильный официальный GRIB-поток с мировым покрытием |
| ICON-Ru | Документированный кандидат для будущего shadow adapter | Публичный WIS-продукт грубее и беднее по полям, чем native-модель |
| Хранилище приложения | PostgreSQL для пользователей; атомарные файлы для моделей и кешей | Надёжное пользовательское состояние без Redis и брокера |
| Кэш точки | Версионированный `gob.gz` + LRU в RAM | Сохраняет `NaN`, компактно хранится и не требует Redis |
| Кэш графиков | PNG-файлы | Отправляются платформам без повторного рендеринга |
| Очередь работ | Ограниченная in-process FIFO и fan-out одинакового ключа | Внешний брокер не нужен; «Горизонт» и астрокупол делят явный лимит активных слотов, до измерений рекомендуется `1` |
| Рендеринг | Pure Go, детерминированные PNG разных размеров | Читаемые таблицы на 72 часа без Python-сервиса |
| Логи | Структурированные текстовые сообщения в stdout | Сбор и ротация средствами Docker |

## 3. Выбор модели по точности и доступности

Большее пространственное разрешение не доказывает лучшую точность каждого параметра. Финальный выбор должен подтверждаться локальной верификацией по наблюдениям. Но архитектура должна начинаться с продукта, который имеет наилучшие технические предпосылки и полный доступный fieldset.

### 3.1. ICON-EU — основной кандидат для приоритетных регионов

DWD публикует ICON-EU на регулярной сетке `0.0625°`, то есть примерно 7 км. Server-side spike 2026-07-19 подтвердил, что текущие открытые element packages имеют `1377 × 657` точек и покрывают `23.5° W–62.5° E`, `29.5°–70.5° N`. Санкт-Петербург и Москва находятся внутри этого фактического домена. Граница всё равно читается из manifest каждого продукта, а не зашивается в router.

Основные свойства:

- нативный шаг 6.5 км, открытая регулярная сетка около 7 км;
- четыре основных запуска `00`, `06`, `12`, `18 UTC` до +120 ч;
- часовой шаг до +78 ч, затем 3 часа;
- дополнительные короткие запуски `03`, `09`, `15`, `21 UTC` до +30 ч;
- surface-поля и необходимые model-level `U`, `V`, `T`, `P`, `QV`, `TKE`, `HHL` доступны на DWD Open Data;
- один и тот же модельный продукт можно использовать для погоды, росы, вертикальных диаграмм и seeing features без смешения моделей.

Источники: [DWD — NWP forecast data](https://www.dwd.de/EN/ourservices/nwp_forecast_data/nwp_forecast_data.html) и [DWD Open Data — ICON-EU GRIB](https://opendata.dwd.de/weather/nwp/icon-eu/grib/).

Это делает ICON-EU базовым production provider для Петербурга, Москвы и других точек внутри открытого домена. Это обоснованный стартовый выбор, но не заявление, что ICON-EU всегда точнее: модель продолжает сравниваться с наблюдениями.

### 3.2. ICON Global — мировой fallback

ICON Global имеет более грубую сетку около 13 км, но покрывает весь мир, имеет стабильный официальный открытый GRIB-поток DWD и тот же класс необходимых полей. Он используется:

- для любой точки вне доступного домена ICON-EU;
- как обязательный baseline в локальной верификации;
- опционально для extended horizon.

Открытый ICON Global приходит на `unstructured_grid`: GRIB ссылается на номера узлов, но не встраивает их координаты. Provider хранит полные native global bundles и один раз скачивает официальную геометрию DWD `icon_grid_0026_R03B07_G.nc`. Для запрошенной точки CDO применяет эту геометрию и выбирает ближайший native-узел; маленький регулярный одноточечный результат передаётся общему ecCodes extractor. Источник не обрезается, вторая мировая raster-копия не создаётся.

Источник: [DWD Open Data — ICON Global GRIB](https://opendata.dwd.de/weather/nwp/icon/grib/).

### 3.3. ICON-Ru: сильная модель, но ограниченный публичный продукт

Нужно различать вычислительную конфигурацию ICON-Ru и публично распространяемые данные.

Официальное описание `ICON-Ru13/6N29` указывает расчётный домен `29.5°–90° N`, все долготы, шаг около 6.5 км, 74 уровня, четыре запуска и горизонт +120 ч. Однако публично описанный WIS 2.0 продукт имеет:

- сетку `0.25° × 0.25°`, а не нативные 6.5 км;
- область `35°–87° N`, `19.5°–193.5° E`;
- только запуски `00` и `12 UTC` до +72 ч;
- высотные ветер/температуру лишь на `925`, `850`, `700`, `500`, `250 hPa`;
- без опубликованных TKE, HHL и полной сетки model levels.

Discovery spike подтвердил origin topic
`origin/a/wis2/ru-roshydromet/data/core/weather/prediction/forecast/short-range/deterministic/limited-area`. Будущий shadow adapter должен подписываться на эквивалентный `cache/a/...` topic одного из TLS Global Brokers WIS 2.0, а не зависеть от незашифрованного origin `mqtt://wis2box.mecom.ru:1883`.

Кроме того, официальное описание текущей системы говорит, что собственного data assimilation пока нет, а начальные данные основаны на DWD ICON Global. Вложенная сетка всё равно может улучшать локальные процессы, но это преимущество нельзя автоматически переносить на публично перегридированный продукт 0.25°.

Источники: [Hydrometcentre — system description](https://mpr.meteoinfo.ru/en/srf-system-about), [ICON-Ru products for WIS 2.0](https://meteoinfo.ru/en/wis2-srf-products-of-wipps-dc-moscow) и [каталог продукции Росгидромета](https://meteoinfo.ru/images/media/books-docs/RHM/catalog-ASDT-20260116.pdf).

Поэтому ICON-Ru WIS остаётся только **кандидатом для будущего shadow provider**. Текущий production-код его не загружает и не оценивает. Если будущая реализация и верификация покажут устойчивое преимущество по конкретному региону/параметру/горизонту, routing можно будет пересмотреть. Стабильный native-поток ICON-Ru 6.5 км потребуется оценивать отдельно.

### 3.4. Начальная production-политика

```text
точка внутри открытого ICON-EU domain -> ICON-EU для всего bundle
точка вне ICON-EU domain             -> ICON Global для всего bundle
ICON-Ru WIS                           -> не подключён; только план shadow-исследования
```

Один provider на весь bundle сохраняет физическую согласованность surface и upper-atmosphere полей и заметно упрощает MVP. Пользователь всегда видит конкретные продукт, сетку и base time.

### 3.5. Как доказать, какая модель точнее

На production-сервер нужно параллельно сохранять одинаковые прогнозные срезы ICON-EU, ICON Global и ICON-Ru WIS для контрольных точек Санкт-Петербурга и Москвы. После наступления valid time они сравниваются с SYNOP/METAR/другими надёжными наблюдениями.

Минимальные метрики:

- MAE/bias температуры и точки росы;
- MAE скорости и круговая ошибка направления ветра;
- ошибка порывов;
- Brier score/contingency metrics для осадков и порогов облачности;
- показатели отдельно для горизонтов `0–24`, `24–48`, `48–72` часа;
- статистика отдельно по региону и сезону.

Первое рабочее решение можно проверить через 30 дней, но router не должен часто переключаться на малой выборке. Накопление и пересчёт верификации продолжаются постоянно. Для seeing нужна отдельная калибровка по астрономическим журналам, DIMM/MASS либо хотя бы по аэрологическим наблюдениям; наземная температура не доказывает качество seeing index.

## 4. Границы MVP

### Входит в MVP

- Telegram и VK с одинаковыми командами и результатами;
- координаты из geo-вложения или текста `широта, долгота`;
- горизонт 72 часа: приземная погода каждый час, высотные профили каждые 3 часа;
- погода, облака по ярусам, риск росы/тумана и события светил на первом графике;
- прогнозный индекс сиинга `1…10`;
- общий почасовой индекс пригодности для астрономии `1…10`;
- семь графиков: почасовая погода, общий почасовой индекс, почасовая облачность по высоте и четыре высотных/seeing-графика;
- автоматическое обновление прогонов и безопасное использование последнего полного прогона;
- локализованный русский/английский интерфейс: Telegram использует `language_code`, а VK пока получает русский по умолчанию, поскольку Group Long Poll его не передаёт;
- прозрачное указание моделей, прогонов и свежести данных.
- локализованные публичные страницы и личный кабинет с отдельными входами в
  обычный прогноз, «Горизонт» и астрокупол.

### Не входит в MVP

- обещание физически измеренного сиинга или шкалы Пикеринга;
- прогноз для конкретной оптической системы телескопа;
- платежи, подписки, вход/привязка VK ID и собственные браузерные архивы
  результатов обычного прогноза или «Горизонта»;
- постоянное хранение истории переписки и точных координат пользователей;
- модели вне семейства ICON;
- горизонт больше 72 часов в основном пользовательском ответе;
- распределённый запуск нескольких экземпляров приложения;
- автоматический shadow-ingest ICON-Ru и observational scoring: исследование источника описано, но production adapter пока отсутствует.

```text

                         |     +-------------------+
DWD ICON Global ---------+---->| Model providers   |
                         |     +-------------------+
ICON-Ru WIS (planned) ---+
                               +---------+---------+
                                         |
                                         v
                               +-------------------+
                               | Atomic model store|
                               +---------+---------+
                                         |
Telegram long polling ---+               v
                          |     +-------------------+
VK Bots Long Poll --------+---->| bot_astrosferum serve    |
                                | request pipeline  |
                                +---------+---------+
                                          |
                      +-------------------+-------------------+
                      v                   v                   v
               point cache        forecast calculator   PNG renderer
                      +-------------------+-------------------+

```

Все блоки после внешних API находятся в одном процессе. На уровне кода они разделены пакетами, а не сетевыми микросервисами.

## 6. Бинарник и режимы запуска

```text
bot_astrosferum serve          # боты + scheduler + обработка запросов
bot_astrosferum sync           # один ручной цикл обновления всех providers
bot_astrosferum doctor         # конфиг, секреты, ecCodes, диски, текущие прогоны
bot_astrosferum render-sample  # графики из fixture без сетевого запроса
```

`serve` запускает:

1. проверку конфигурации и каталогов;
2. Telegram poller;
3. VK poller;
4. bounded worker pool пользовательских запросов;
5. внутренний model sync scheduler;
6. очистку устаревших прогонов и кэша;
7. обработку сигналов `SIGTERM/SIGINT` с graceful shutdown.

Ручной `sync` и scheduler используют общий файловый lock. Два обновления одновременно не запускаются.

## 9. Минимальная доменная модель

```go
type Location struct {
    Latitude  float64
    Longitude float64 // canonical range: -180..180
    TimeZone  string  // IANA name; UTC on resolver failure
}

type RunRef struct {
    Provider  string
    RunID     string
    BaseTime  time.Time
    Grid      string
    Horizon   time.Duration
}

type ForecastFrame struct {
    ValidAt time.Time
    Surface SurfaceFields
    Levels  []PressureLevel
    Astro   AstroFields
}

type ForecastBundle struct {
    Location Location
    Run      RunRef
    Frames   []ForecastFrame
}

type AstroConditions struct {
    SeeingIndex     float64 // 1..10, forecast index
    ConditionsScore float64 // 1..10, overall astronomy suitability
    Weather         WeatherSummary
    Dew             DewRisk
    Algorithm       string
}
```

Внутри используются SI-единицы: K или °C только в явно названных полях, Pa, m, m/s, доли `0…1`. Конвертация в подписи выполняется на границе рендера/ответа.

У каждого рассчитанного ряда сохраняется provenance: provider, run ID, grid, реальные координаты выбранного узла, время извлечения и версия набора полей.

## 10. Граница provider

Реальная граница serving намеренно меньше универсального provider framework:

```go
type ForecastStore interface {
    Vertical(context.Context, forecast.Location) (forecast.VerticalSeries, error)
    Surface(context.Context, forecast.Location) (forecast.SurfaceSeries, error)
    Cloud(context.Context, forecast.Location) (forecast.CloudSeries, error)
}
```

Реализованные stores:

- `iconeu`: DWD ICON-EU, основной provider в доступном европейском домене;
- `iconglobal`: DWD ICON Global вне домена ICON-EU;
- `model.CoverageFallback`: небольшой двухветочный router между ними.

Sync clients и schedulers остаются конкретными: реальных providers пока два. `Coverage` включает:

- геометрию домена и правила нормализации долготы;
- доступные поля и уровни;
- доступные сроки и временной шаг;
- максимальный горизонт;
- фактическое разрешение продукта.

Будущий проверенный provider сможет реализовать `ForecastStore` без изменений обработчиков платформ, расчётов и рендера; спекулятивного adapter сейчас нет.

## 11. Выбор источника

| Условие | Production bundle | Примечание |
|---|---|---|
| Точка внутри доступного ICON-EU element-package domain | ICON-EU | Surface и atmosphere из одного run |
| Точка вне доступного ICON-EU domain | ICON Global | Вся остальная территория мира |
| Срок > основного горизонта 72 ч | Provider-specific до +120 ч | Позднее, не показывается в основном MVP-ответе |
| ICON-Ru WIS | Не участвует | Только verification/shadow pipeline |

Домен берётся из manifest фактического продукта. Spike подтвердил открытую границу до `62.5° E`, но router не предполагает, что она никогда не изменится.

Fallback никогда не происходит молча: provider, сетка и run печатаются в тексте и в footer каждого PNG. Router не смешивает два provider в одном production bundle до тех пор, пока верификация не докажет пользу такого смешения.

## 12. Синхронизация модели

### 12.1. Полный цикл

1. Provider определяет самый новый потенциальный run.
2. Проверяет наличие обязательного последнего срока и всех обязательных полей.
3. Создаёт `data/models/<provider>/incoming/<run-id>/`.
4. Скачивает файлы во временные имена `*.part` с ограничением параллелизма.
5. Проверяет HTTP size, распаковку, `grib_ls`, ожидаемые параметры, уровни и сроки. Valid time строится из `step`, `stepUnits` и `stepRange`: DWD фактически выдаёт, например, `180 m`, а не обязательно `3 h`.
6. Сообщения ICON Global сохраняются на полной native-сетке и группируются по сроку. При извлечении точки CDO применяет официальную статическую геометрию DWD и выбирает ближайший native-узел; ICON-EU этот шаг пропускает.
7. Записывает `manifest.json`, затем делает `fsync` критичных файлов.
8. Переименовывает каталог `incoming/<run-id>` в `runs/<run-id>`.
9. Только после готовности pressure, thermodynamics, почасовых surface и native-level cloud данных атомарно переключает symlink `current` на новый run.
10. После публикации удаляет старые прогоны и недействительные кэши.

Неполный run никогда не становится current.

Текущий почасовой контракт ICON-EU разделён на два независимо валидируемых
набора. `surface-hourly-v17` содержит 17 single-level сообщений на каждый
`f000…f078`, включая `MH`/`mld` в метрах. `cloud-hourly-v4` содержит ровно
187 сообщений на каждый час: `CLC/P/T/QC/QI` на всех 27 выбранных full levels,
`U/V` на последовательных нижних levels `58…74` и `TKE` на half levels
`58…75`; отдельный time-invariant bundle хранит нужные `HHL`. Manifest
переключается только после проверки количества, shortName, level, размера и
SHA-256 каждого файла.

ICON Global публикует тот же почасовой cloud/PBL контракт на полной native
grid. Эквивалентные по высоте индексы: `71,76,81,86,91,94,96,
98,100,102,104…120` для `CLC/P/T/QC/QI`, `104…120` для нижних `U/V` и
`104…121` для half-level `TKE/HHL`. Это индексы ICON-EU со сдвигом `+46`,
проверенным по фактическим HHL в общей области. Полное 79-часовое расширение
валидируется в staging-каталоге и открывается одной атомарной заменой manifest.
Перед общим cloud extractor point-путь применяет официальную Global grid,
поэтому rendering и Overall используют одинаковые типы и формулы для обоих
providers.

DWD Global публикует model-level TKE только до `+48 ч`. Bundles до этого срока
содержат 187 сообщений; bundles `+49…+78 ч` сохраняют все
`CLC/P/T/QC/QI/U/V` (169 сообщений) и намеренно не содержат TKE. Поэтому cloud
heatmap остаётся почасовой на всём горизонте, а гибридный TKE/HMNSP99 Overall
заканчивается на последнем native-TKE сроке без экстраполяции турбулентности.
Pressure-level wind/seeing диагностика продолжается.

В следующих циклах EU и Global symlink `current` не переключается после
промежуточного этапа. Он остаётся на предыдущем полном run до готовности всех
нужных пользовательскому прогнозу наборов, затем один раз заменяется атомарно.

### 12.2. Состояния run

```text
discovered -> downloading -> validating -> ready -> published
                    |              |
                    +---- failed --+
```

Состояние хранится в `manifest.json`; оно позволяет продолжить загрузку после рестарта и не скачивать валидные файлы повторно.

### 12.3. Состав manifest

- provider и продукт;
- run ID и base time UTC;
- фактический домен/сетка;
- список полей, уровней и forecast steps;
- размер и SHA-256 каждого итогового файла;
- версия preprocessing fieldset;
- время загрузки и валидации;
- флаг `complete`.

### 12.4. Политика хранения и диска

- хранить два полных опубликованных прогона production providers вместе с их
  surface и model-level cloud bundles;
- для ICON-Ru shadow хранить один run либо только извлечённые контрольные точки;
- очищать зависшие `incoming` старше 24 часов;
- point cache хранит не более двух run и 512 точек на run; render cache — не более 256 комплектов и 48 часов;
- очищать незавершённые cache/render staging-файлы старше часа и модельные `incoming` старше 24 часов;
- не начинать sync при свободном месте ниже `min_free_space`;
- для production-сервера начальное безопасное значение `min_free_space: 150GiB`;
- первым этапом скачивать только необходимые поля и 3-часовые высотные сроки;
- при нехватке места удалять disposable cache, затем старый run; current run не удалять.

## 13. Извлечение точки

Собственный GRIB-парсер не нужен. ecCodes поддерживает выбор ближайшего узла регулярной сетки через `grib_get -l latitude,longitude,1`; это документировано в [официальной справке ecCodes](https://confluence.ecmwf.int/display/ECC/grib_get). ICON-EU уже имеет регулярную сетку. Для ICON Global CDO сначала создаёт один регулярный point по официальной native-геометрии, после чего используется тот же нормализованный extractor.

Поток извлечения:

1. Нормализовать и проверить координаты.
2. Provider определяет ближайший узел своей сетки.
3. Сформировать grid cell ID из provider + grid ID + фактических координат узла.
4. Проверить point cache.
5. Для cache miss вызвать ecCodes для каждого объединённого `fNNN.grib2`.
6. Проверить единицы, missing values и диапазоны.
7. Преобразовать в общую `PointSeries`.
8. Атомарно записать `gob.gz` в point cache и поместить bundle в ограниченный RAM LRU.

Координаты пользователя вручную не округляются. Две близкие точки разделяют кэш только тогда, когда provider выбрал для них один и тот же модельный узел.

Опциональный Horizon использует другой путь намеренно: ему нужен полный период
во множестве пространственных ячеек. Для одного запроса он один раз строит
CDO-план ближайших соседей (`gennn`) по всем дедуплицированным lookup cells и
переиспользует неизменяемые веса при чтении pressure/surface/cloud/HHL через
`remap + outputtab`. Отдельный цикл `grib_get` для каждого midpoint и
промежуточный GRIB не создаются. Результат попадает в отдельный bounded Horizon
cache из раздела 29, а не в обычный point cache. Обычный ICON-EU прогноз этот
путь не использует: он по-прежнему выполняет `grib_get -l` и обслуживает
повторы через point cache, RAM LRU и single-flight.

Provider-specific ключи point cache:

```text
ICON-EU:     point-v6-native-cloud-mass-mh/<run>/<grid-cell>.gob.gz
ICON Global: point-v2-native-cloud/<run>/<grid-cell>.gob.gz
```

## 14. Нормализация и контроль качества

До расчётов выполняются:

- преобразование Kelvin → Celsius и Pa → hPa только в явно нужных представлениях;
- нормализация longitude и времени в UTC;
- проверка монотонности valid time;
- приведение accumulated precipitation к осадкам за интервал;
- запрет отрицательной облачности/влажности и значений выше 100%;
- распознавание `missingValue` из GRIB;
- проверка физически невозможных значений;
- сохранение почасовой сетки surface/cloud и интерполяция 3-часового
  pressure-level профиля только к её valid time;
- сохранение маски missing data вместо подстановки нуля.

Если отсутствует необязательное поле, соответствующий показатель получает
состояние `unavailable` или `partial`; весь ответ не должен падать из-за одного
необязательного слоя. Отсутствующие данные нельзя изображать как благоприятные
условия.

## 15. Расчёты

### 15.1. Ветер

```go
speed := math.Hypot(u, v)
direction := math.Mod(math.Atan2(-u, -v)*180/math.Pi+360, 360)
```

Минимальная угловая разница:

```go
d := math.Mod(math.Abs(a-b), 360)
if d > 180 {
    d = 360 - d
}
```

Основной динамический признак — векторный сдвиг между соседними уровнями:

```text
shear = hypot(u₂-u₁, v₂-v₁) / abs(z₂-z₁ in km)
```

Скалярная разница скорости больше не строится: она вводит в заблуждение при неодинаковом расстоянии между уровнями. Если `min(speed₁,speed₂) < 2 m/s`, разница направления отображается как `0°`: азимут почти штилевого ветра неустойчив, а его вклад в условия наблюдений мал. `NaN` сохраняется только для действительно отсутствующих данных.

### 15.2. Вертикальные уровни

Целевая шкала графиков:

```text
1000, 975, 950, 925, 900,
850, 800, 750, 700, 650,
600, 550, 500, 450, 400,
350, 300, 250, 200, 150,
100, 70, 50 hPa
```

Давление подписано слева, а справа каждый heatmap показывает среднюю фактическую геопотенциальную высоту `FI/g` соответствующего pressure level. Для облачной карты высота середины полного модельного слоя получается из соседних `HHL`; постоянная стандартно-атмосферная таблица используется только как fallback для старого bundle.

Входной cloud/PBL subset сохраняет разреженные уровни свободной атмосферы и
непрерывную нижнюю часть:

```text
25, 30, 35, 40, 45, 48, 50, 52, 54, 56, 58, 59, 60, 61, 62,
63, 64, 65, 66, 67, 68, 69, 70, 71, 72, 73, 74
```

На всех 27 уровнях есть `CLC/P/T/QC/QI`; последовательные full levels `58…74`
дополнительно содержат `U/V`, а TKE берётся с ограничивающих half levels
`58…75`.
`HHL` задаёт фактическую геометрию и поверхность. Непрерывность нижней части
нужна для центрального градиента `theta` и трапецеидального интегрирования PBL,
а разреженная верхняя часть — для облачной карты. Subset versioned; manifest
хранит точный набор каждого run.

Обычный точечный расчёт уже использует высоту model surface HHL в ячейке ICON.
Она задаёт начало AGL для нативных высот облаков, динамическую границу mixed
layer и интеграл турбулентности ground layer. Поэтому высота не игнорируется,
но не добавляется повторно как самостоятельный бонус или штраф индекса: это
дважды учло бы model geometry и создало видимость локальной точности, которой у
ячейки HHL размером около 7 км нет. HHL — не локальный DEM и не модель optical
skyline; поле не разрешает локальный рельеф и препятствия. Horizon дополнительно
использует то же поле только для грубого пересечения луча с рельефом по
направлению.

Пограничный слой TKE и свободная атмосфера HMNSP99 сохраняются в одном
упорядоченном кусочно-линейном профиле `Cn2`. По нему согласованно вычисляются
сиинг, `tau0`, `theta0`, эффективные высота и скорость ветра турбулентности,
`FracGL250/500/1000` для фиксированных высот, сиинг свободной атмосферы выше
500 м и геометрическая полнота профиля. Динамическая доля PBL не смешивается с
похожими на MASS фиксированными `FracGL`; последние являются модельной
диагностикой, а не измерением MASS.

Данные интерполируются на эту шкалу только внутри диапазона реально доступных уровней. Экстраполяция выше или ниже доступной атмосферы запрещена; ячейки показываются как missing.

### 15.3. Прогнозный индекс сиинга по ветру

Название в UI: **«Прогнозный индекс сиинга по ветру»** / **Forecast Wind Seeing Index**, а не «точный сиинг» и не «шкала Пикеринга».

Это сохранённый сравнительный wind-only diagnostic, а не физический seeing,
используемый в Overall. Признаки версии `seeing-v1`:

- vector shear между соседними высотными уровнями;
- скорость ветра в районе струйного течения, прежде всего 300–200 hPa;
- вертикальный градиент потенциальной температуры/статическая устойчивость;
- TKE в нижней и свободной атмосфере, только если поле реально доступно;
- приземный ветер и порывы;
- штраф за missing data и слишком старый run.

Каждый признак переводится в безразмерный penalty `0…1` конфигурируемой piecewise-linear функцией. Затем:

```text
penalty = weighted_mean(available feature penalties)
seeing  = clamp(1, 10, 10 - 9 * penalty)
```

Вес недоступного признака исключается из знаменателя, но confidence снижается. Вместе с индексом рассчитывается `confidence: low|medium|high`. Коэффициенты и пороги находятся в конфиге и входят в version/hash кэша.

До валидации по DIMM, MASS или журналам наблюдений индекс является
эвристическим сравнительным прогнозом. Overall не умножается на него:
векторный shear уже входит в HMNSP99, а ветер дополнительно учитывается в
физическом `tau0`, поэтому повторный полный штраф был бы двойным учётом.

### 15.4. Погода — обязательная отдельная строка

`WeatherSummary` рассчитывается отдельно от сиинга и общего score.

Базовая последовательность классификации:

1. Определить тип и интенсивность осадков.
2. Если существенных осадков нет, классифицировать общую облачность.
3. Добавить значимые порывы/туман как модификатор.

Начальные категории облачности, калибруемые конфигом:

- `0–20%`: ясно;
- `20–50%`: малооблачно/переменная облачность;
- `50–80%`: облачно;
- `80–100%`: пасмурно/сильная облачность.

Пример обязательной строки ответа:

```text
Погода: 21:00–03:00 облачно, после 03:00 небольшой дождь; порывы до 9 м/с.
```

### 15.5. Роса — обязательная отдельная строка

Для росы нельзя выдавать неподтверждённую «вероятность в процентах». Выдаётся риск `низкий / средний / высокий` и ожидаемое окно.

Признаки `dew-v1`:

- spread `T₂m - Td₂m`;
- относительная влажность;
- температура поверхности `T_G`, если provider её предоставляет;
- ветер у поверхности;
- низкая облачность и осадки;
- тренд температуры и spread в предыдущие сроки.

Если `T_G` недоступна в выбранном продукте, алгоритм использует spread/RH/wind и снижает confidence. Пороги находятся в конфиге, а не зашиты в platform adapter.

Пример обязательной строки:

```text
Роса: высокий риск с 00:00 до 05:00; минимум T−Td 0.8 °C.
```

Риск росы является только эксплуатационной подсказкой: он помогает заранее подготовить обогреватель, бленду или салфетки для оптики. Он не ухудшает прогнозный индекс сиинга, не снижает общий индекс условий и не является hard gate; при защите оборудования наблюдения могут оставаться полноценными.

### 15.6. Общий почасовой индекс пригодности

Это не ещё один физический «сиинг» и не универсальная научная шкала `1…10`,
а аудируемое отображение пригодности часа для визуальной астрономии и
астрофотографии. Роса в индекс не входит. Осадки за интервал от настраиваемого
порога обнаружения `0.05 mm за часовой кадр` становятся бинарным
эксплуатационным запретом:
индекс часа равен `1.0`, а плавный штраф по интенсивности из одного
детерминированного члена модели не придумывается.

Оптическая турбулентность рассчитывается гибридно. Для каждого часа граница
PBL берётся из single-level `ICON MH` и ограничивается
`h_PBL=clamp(MH,500,2000) m AGL`. От поверхности до `h_PBL` native ICON
`T/P/TKE/HHL` даёт `Cn²` по формуле Masciadri
`3.35e−6·P^[2(1−2R/cp)]·theta^(−10/3)·|dtheta/dz|^(4/3)·TKE^(2/3)`;
центральный градиент вычисляется на последовательных model levels `58…74`,
интегрирование выполняется трапециями от `HHL75`. Выше того же почасового
`h_PBL` применяется HMNSP99 к pressure-level `T/U/V/FI`.
`J_total=J_ground+J_free` переводится в
zenith long-exposure seeing на `500 nm` стандартной формулой. Ветер входит в
`tau0=[2.910·(2π/lambda)²·integral(Cn²·|V|^(5/3)dz)]^(−3/5)`. Векторный shear
HMNSP99 уже содержит изменение направления, поэтому отдельный множитель
`direction delta` не добавляется. На каждом интервале трапеция усредняет
концевые значения `Cn²·|V|^(5/3)`; скорость не усредняется до степени `5/3`,
иначе выпуклый ветровой момент занижался бы по неравенству Йенсена.

Скалярный час Overall отклоняется, если вертикальная полнота профиля либо
геометрическая полнота момента `h^(5/3)` ниже `90%` или верх модели/профиля
ниже `15 км AGL`. Более строгий статус `complete` требует обе полноты не ниже
`99%` и верх не ниже `18 км AGL`. Поэтому физически вычислимый профиль
`15…18 км` допускается только как частичный, а любой
`ProfileQuality != complete` ставит на графике знак `!`.

Seeing и `tau0` отображаются логарифмически между `.env`-границами
`0.5…2.0 arcsec` и `5.2…1.6 ms`; `tau0` входит внутрь turbulence-quality с
мягким весом `0.25`. Выпуклая utility-смесь ограничивает совместный штраф
seeing/`tau0` величиной `25%`, не меняя физические значения. Эти опоры согласованы с
[категориями ESO](https://www.eso.org/sci/observing/phase2/ObsConditions.CRIRES.html),
но сама композиция остаётся инженерной.

Облачная часть Overall использует фазовую оптическую толщину из `TQC/TQI`:
`tau_phase=3·Qext·CWP/(4·rho·r_eff)` и
`B_cond=C·(1−exp(−tau/C))`. Диагностический `CLC/CLCT` может сосуществовать с
почти нулевым grid-scale condensate, поэтому применяется tier-aware
unresolved-cloud guard: low `0.45·C`, middle `0.55·0.45·C=0.2475·C`, high
`0.18·0.45·C=0.081·C`. Это инженерная консервативная неопределённость, а не
заданная физическая opacity ярусов; физический `B_cond` всегда выигрывает,
когда он больше. В Overall guards из `CLCL/CLCM/CLCH` объединяются по
random overlap и ограничиваются диагностированным покрытием.

Тепловая карта применяет тот же optical-depth kernel и tier-aware guard
отдельно на каждом native level. Для неё путь конденсата вычисляется из
`QC/QI` и массы именно этого слоя:
`m_air=P_Pa/(287.05·T)·abs(HHL[k]−HHL[k+1])`, а не из `Delta p` между
разреженными выбранными уровнями. Из-за вертикального расчёта карты и
total-column расчёта Overall их численные значения не обязаны быть
идентичны; общей остаётся физика оптической толщины и guard policy.

Tier-aware guard остаётся конфигурируемым fallback: согласованные diagnostic
`QC_DIA/QI_DIA` отсутствуют в публичном ICON-EU Open Data, а доступный
`CLCT_MOD` является visualization field и, по документации DWD, игнорирует
cirrus при одной высокой облачности — неприемлемо для астрономии.

Возможный/высокий туман дают множители `0.75/0.10`. Приземный ветер — лишь
мягкая практическая помеха: smoothstep начинается при `8.5 m/s` для среднего
ветра и `12 m/s` для порывов, достигает максимума при `15/22 m/s`, а общий
штраф ограничен 20%. Итог при defaults `w_seeing=1`, `w_cloud=2`:

```text
q_turbulence = q_seeing^w_seeing * [1−0.25·(1−q_tau)]
f_turbulence = 0.75 + 0.25·q_turbulence
normalized = f_turbulence * q_cloud^w_cloud
             * q_surface_wind * q_fog * q_precip
index = 1 + 9 * clamp(normalized, 0, 1)
```

Модуль отрисовки распределяет точную потерю `1-normalized` между
турбулентностью, облачной преградой, приземным ветром, туманом и осадками с
помощью не зависящего от порядка значения Шепли. Внизу столбца остаётся сам
индекс, а пять цветных сегментов потери замыкают столбец ровно на 10. Знак `!`
означает частичные входные данные, а не вероятность.

Все пороги и множители входят в cache/version hash. Обезличенный исторический
контрольный пример показал причину прежнего оптимизма: pressure-level
HMNSP99 давал около `0.70…0.77″` без PBL. Диагностика с фиксированными 2 км
дала `2.221″/3.644″`; после подключения почасового `MH=396 m` правило
clamp-500 дало `1.9145″` (`f042`) и `2.5478″` (`f048`). Это server-only
регрессии, не наблюдательная калибровка. Production run `2026072106`
опубликован и прошёл post-deploy проверку контрольного примера. Абсолютная
оценка требует DIMM/MASS/SCIDAR или журналов наблюдений в целевых регионах;
UI продолжает явно называть её model-derived. Полные выкладки и источники —
в [научной методике и расчётной записке](scientific-method.ru.md).

### 15.7. Зенитная эффективность в опорной полосе Johnson V

На графике 2 только в астрономическую ночь накладывается отдельное кольцо,
если полный опорный расчёт доступен и эксплуатационно пригоден. Контракт
`reference-v-band-zenith-efficiency-v2` с атмосферной моделью
`reference-v-band-spectrl2-ks91-v3` описывает слабый точечный источник вдоль
направления **геометрического зенита, усреднённого по ячейке сетки**, полосу
SVO Generic/Johnson.V, длинную экспозицию, доминирование фонового шума,
ограничение сиингом и отсутствие адаптивной оптики. Это не мгновенное точечное
измерение столба и не направление на сопровождаемую цель:

```text
G = скорость_фотонов_источника² / (яркость_фона * эквивалентная_по_шуму_площадь_PSF)
reference_index = 1 + 9 * clamp(G / G_benchmark, 0, 1)
```

ICON задаёт `P/T` самого нижнего доступного полного нативного уровня, его
высоту из соседних границ `HHL`, `HHL` поверхности модели, PWV (`TQV`),
облачное пропускание и сохранённый сиинг на 500 нм. Reference V
восстанавливает фактическое давление на поверхности модели сухим
гидростатическим переносом через нижний модельный промежуток:

```math
p_s=p_l\exp\!\left[\frac{g_0(z_l-z_s)}{R_dT_l}\right].
```

Маркер происхождения —
`icon-lowest-model-level-p-hydrostatic-to-hhl-surface-v1`. `PMSL` остаётся
приведённым к среднему уровню моря полем погодного графика и никогда не входит
в SPECTRL2. При отсутствии или некорректности относящихся к тому же часу
`p_l/T_l/z_l/z_s` Reference V становится частичной; подстановки `PMSL` или
стандартной атмосферы нет, а перенос разрешён только для промежутка не более
`1 км`. Сухое приближение с постоянной `T_l` на этом
коротком промежутке не разрешает влажность, подсеточный рельеф и кривизну
профиля температуры. Отдельный ограниченный поставщик NASA GEOS-CF даёт
почасовые `AOD550` и полный столб озона со своими циклом, актуальностью и
происхождением. SPECTRL2
интегрирует рэлеевское и аэрозольное ослабление, поглощение водяным паром,
озоном и смесью газов по отклику Johnson V; фотонно-взвешенная смесь гауссовых
функций рассеяния точки даёт точную эквивалентную по шуму площадь, а KS91 —
явно обозначенное резервное приближение лунного фона в зените. Искусственная
засветка исключена и остаётся отдельной строкой атласа.

Полное облачное пропускание ICON ослабляет только источник:
`S=S_clear*T_cloud`. Поскольку яркость рассеянного облаками неба недоступна,
естественный и лунный фон чистого воздуха удерживается как консервативный
нижний предел. При неизменной PSF это даёт
`G_cloud=T_cloud²*G_clear`. Квадратичный отклик является явным ограничением, а
не расчётом переноса излучения в облаках. При нулевом атмосферном пропускании
`ExtinctionMag` пропускается/равна `null`, а
`OpaqueTransmission=true`, поскольку логарифмическая величина не конечна.

GEOS-CF обрабатывается без отказа основного прогноза: тайм-аут, устаревший
кадр состава или отсутствие компоненты убирают либо помечают кольцо, но не
блокируют ICON. Reference V не умножается на универсальный Overall: это разные
контракты наблюдения. `theta0`, `FracGL`, PWV и сцинтилляция также не получают
универсальных штрафов без явно заданных цели, полосы, телескопа и режима.
Атмосферную FWHM для конкретной цели можно отдельно пересчитать по воздушной
массе Kasten-Young и закону `X^(3/5) lambda^(-1/5)`.

Отсутствие сиинга, восстановления давления на станции или состава атмосферы
явно даёт частичный результат и не позволяет показать кольцо. При высоком
риске тумана либо запрете по осадкам Reference V эксплуатационно недоступна,
поэтому её маркер не рисуется, даже если исходные диагностики были рассчитаны.

Сетевой тайм-аут GEOS-CF равен `60 с`; необязательная операция живёт в корневом
контексте сервиса не более `65 с` и отменяется при остановке приложения, а не
при отключении одного пользователя. Пользовательский прогноз присоединяется к
ней не более чем на `5 с`. При холодном промахе семь графиков ICON продолжают
строиться, не ожидая полный набор состава, а успешная операция может прогреть
кэш в памяти. Одинаковые наборы уровней объединяются; разные загрузки делят
ограничитель `ASTRO_FORECAST_CONCURRENCY`, и при его заполнении новая
необязательная загрузка не запускается и завершается без отказа ICON.

### 15.8. Засветка точки

Засветка — постоянное свойство площадки, а не почасовой метеорологический параметр. Она показывается в текстовом блоке и **не входит в Overall Astronomy Index**.

Источник — последний опубликованный [Light Pollution Atlas Дэвида Лоренца](https://djlorenz.github.io/astronomy/lp/). На 21 июля 2026 года это Atlas 2024: годовая радиация VIIRS 2024 преобразована моделью переноса, поглощения и рассеяния света в искусственную яркость неба в зените. Это актуальнее World Atlas 2015 и физически корректнее прямого преобразования свежего пикселя VIIRS: спутник измеряет излучение поверхности, а наблюдателю важен рассеянный свет от всех окружающих источников.

Числовые тайлы имеют шаг `1/120°`, около `30″`. Для точных пользовательских координат сервис билинейно интерполирует **LPI** четырёх соседних узлов, после чего вычисляет `SQM = 22 − 2.5·log10(1+LPI)` в `mag/arcsec²`. LPI — отношение искусственной яркости к принятому естественному фону. В ответе приводятся LPI, SQM, год атласа и ориентир Бортля.

Шкала Бортля субъективна и оценивает всё небо по видимым объектам, а атлас моделирует только зенит. Поэтому UI пишет «ориентир Бортля», не выдаёт его за измерение и объединяет самые яркие условия в `8–9`, где один SQM не позволяет честно различить классы. Реальное значение зависит от прозрачности, аэрозоля, снега, локальных фонарей и направления световых куполов; точнее карты только измерение SQM/всего неба на площадке.

Год атласа явно фиксируется параметром `providers.light_pollution.atlas_year` / `ASTRO_LIGHT_POLLUTION_ATLAS_YEAR`; production сейчас использует `2024`. Runtime не ищет и не включает новую версию автоматически: оператор меняет год только после проверки источника и тестового запроса. Скачивается только нужный координатам тайл `5°×5°`; он атомарно кэшируется в `data/light-pollution/lorenz-atlas/<year>`. Хранятся не более двух последних годовых каталогов, поэтому кэш не растёт бесконечно.

## 16. Астрономические величины и локальное время

- расчёты внутри системы выполняются в UTC;
- для каждого запроса timezone заново определяется по координатам, которые прислал пользователь;
- пользователю время показывается в локальной IANA timezone именно этой точки, с учётом исторического/сезонного UTC offset на дату прогноза;
- timezone определяется офлайн по координатам; если resolver не уверен, UI явно показывает UTC;
- polygon lookup использует `tzf v1.2.3` с embedded boundary data, без сетевого API;
- в бинарник включается Go timezone database через `time/tzdata`, чтобы контейнер не зависел от состояния host;
- восход и заход Солнца, восход и заход Луны, фаза, освещённость и день лунного цикла рассчитываются офлайн по алгоритмам Meeus (`github.com/soniakeys/meeus/v3`, MIT); пересечения горизонта уточняются внутри местных календарных суток до секунды, а UI округляет их до минуты;
- regression-тест для Санкт-Петербурга 20 июля 2026 ограничивает расхождение с предоставленным эталоном двумя минутами для каждого из четырёх событий;
- независимый regression-тест для Москвы (`55.7558, 37.6173`) на ту же дату сравнивается с сервисом [USNO Complete Sun and Moon Data for One Day](https://aa.usno.navy.mil/data/api.html): эталон Солнце `04:14/20:57`, Луна `12:25/22:33`; pure-Go результат укладывается в две минуты;
- все текстовые сроки и все графики одного ответа используют одну найденную timezone точки и обязательно подписывают её, например `Europe/Moscow · MSK (UTC+3)` или `UTC` при fallback.

## 17. Референсные графики и контракт рендера

MVP строит семь изображений:

1. **Почасовая погода на 72 часа** — погода, риск росы и тумана, `Прозрачность %`; стрелки показывают поток ветра. В строках Солнца, Луны, Юпитера и Сатурна остаются только значок события и время без слов «восход/заход»; фаза Луны отдельна. Фон и легенда отделяют день, светлые сумерки (`0…−12°`), астрономические сумерки (`−12…−18°`) и ночь (`<−18°`). Граница берётся из рассчитанного пересечения высоты Солнца и рисуется в субчасовой позиции пикселя, а не округляется до model term.
2. **Overall Astronomy Index** — увеличенные почасовые составные столбцы
   `1…10`. Нижняя часть показывает сохранённую пригодность; цветные сегменты
   сверху — точное разложение Шепли для потерь от оптической турбулентности,
   эффективной облачной преграды, приземного ветра, тумана и осадков. Полный
   столбец замыкается на 10. Подпись содержит итог и `epsilon/T%`; осадки от
   `R_1h >=0.05 mm` дают запрет, а `!` означает частичные данные. Только в
   астрономическую ночь поверх графика ставится кольцо отдельной полной и
   эксплуатационно доступной эффективности Reference Johnson V вдоль
   геометрического зенита, усреднённого по ячейке сетки; в Overall она не
   входит. Фон и
   легенда под осью используют те же четыре класса высоты Солнца, что 1/7, с
   субчасовыми позициями границ; значение индекса от них не меняется.
3. **Эффективная облачная преграда ICON по высоте/времени** — почасовая доля блокируемого небосвода по 27 model levels: разреженным в свободной атмосфере и непрерывным `58…74` внизу. Для каждого слоя используются прямые `CLC`, `T`, жидкий `QC`, ледяной `QI` и нативная толщина `|HHL[k]−HHL[k+1]|`; масса воздуха равна `P/(Rd·T)·dz`. Базовая преграда `C·(1−exp(−τ_layer/C))` получает tier-aware guard `45%/24.75%/8.1%` от `C` для низкого/среднего/высокого яруса, но более сильная физическая `QC/QI`-преграда всегда сохраняется. Эти проценты — инженерная неопределённость, не opacity. Overall использует total-column и random overlap трёх агрегированных ярусов, поэтому его `T%` и отдельная ячейка карты не обязаны совпадать. Цвет и число показывают effective obstruction `0…100%`, а не покрытие или объёмную плотность.
4. **Wind speed vs pressure/time** — тепловая карта скорости ветра, m/s.
5. **Vertical vector wind shear vs pressure/time** — `hypot(Δu,Δv)/|Δz|`, m/s/km.
6. **Wind direction delta vs pressure/time** — минимальная угловая разница; при слабом ветре `<2 m/s` отображается `0°`.
7. **Forecast Wind Seeing Index vs time** — прежний wind-only диагностический график `1…10`; текст `96%` внутри столбца показывает условную уверенность по дальности срока.

Контракт PNG:

- weather-таблица `3200×1080`, общий индекс `4320×1600`, облачная карта `3200×1100`, остальные изображения `1280×960`; формат PNG;
- крупные подписи, пригодные для телефона;
- давление по вертикали: `50 hPa` сверху, `1000 hPa` снизу;
- время по горизонтали: каждый час для weather-таблицы, шаг 3 часа для высотных графиков;
- числовое значение в ячейке только при достаточном контрасте;
- missing data — серый цвет и знак `×`, не ноль;
- границы календарных суток и затенение дневного времени;
- под каждой тепловой картой непрерывная цветовая legend с минимумом, серединой, максимумом и смыслом тёмного/светлого цвета;
- координаты отображаются с ограниченной точностью;
- в footer: provider/product, base run UTC, grid, algorithm version и время генерации;
- одинаковая цветовая шкала между запросами одной версии renderer;
- название seeing-графика не содержит `Pickering Scale` до физической калибровки.

Пиктограммы weather-таблицы имеют встроенную легенду также для двух уровней тумана. Высокий риск требует прямого `ICON VIS <1 km`, `RH ≥95%` и `T−Td ≤1.5°C`; возможный — `VIS <5 km`, `RH ≥90%`, `T−Td ≤2.5°C`. Проверка насыщения не даёт назвать дым, сухую дымку либо осадки туманом только из-за плохой видимости. Порог 1 км следует определению [WMO International Cloud Atlas](https://cloudatlas.wmo.int/fog-compared-with-mist.html).

Три строки показывают официальные ICON-EU `CLCL/CLCM/CLCH`. Цвет покрытия: белый `<10%`, синий `10–49%`, оранжевый `≥50%`; это покрытие, не оптическая толщина. [ESO отдельно указывает](https://www.eso.org/sci/observing/phase2/ObsConditions.CRIRES.html), что даже тонкие cirrus дают вариации прозрачности более 10%, поэтому верхний ярус не игнорируется.

Строка `Прозрачность %` — версия эвристики, а не физическое пропускание: основным множителем служит максимум `CLCT/CLCL/CLCM/CLCH`, уточнениями — приземная горизонтальная видимость `VIS` и полный столб водяного пара `TQV`/PWV. Для `transparency-proxy-v0`: `C=max(CLCT,CLCL,CLCM,CLCH)`, `V=clip((VIS_km−5)/45)`, `W=1−clip((PWV_mm−5)/35)`, результат `100·(1−C/100)·(0.65+0.25V+0.10W)`. Коэффициенты — некалиброванный KISS-порядок сортировки часов, поэтому название proxy сохраняется в легенде и `/start`, хотя короткая подпись строки — «Прозрачность %».

DWD определяет [`VIS` в метрах и `TQV` в kg/m²](https://isabel.dwd.de/DWD/publikationen/dokumentation/grib/DWD_GRIB2_PARAMETER.htm); значение `kg/m²` численно равно мм PWV. Для настоящей оптической прозрачности нужны как минимум прямые измерения AOD/extinction: [DWD получает AOD и PWV фотометрией Солнца, Луны и звёзд](https://www.dwd.de/EN/research/observing_atmosphere/lindenberg_column/radiation/photometry.html). Поэтому proxy предназначен только для сравнения часов одного прогноза и не годится для абсолютной фотометрии.

Капля обозначает малый `T−Td` и возможную росу; подпись — «Роса — подготовить обогрев/бленду», без штрафа к seeing. Координата X каждого значка события соответствует расчётному времени между часовыми колонками. Pure-Go приближение Юпитера и Сатурна использует средние орбитальные элементы с light-time итерацией и служит для планирования; для требовательной работы результат нужно сверять с [JPL Horizons](https://ssd.jpl.nasa.gov/horizons/manual.html).

Предпочтительная реализация — один pure-Go renderer на базе `gonum/plot` и `golang.org/x/image`, с вшитым шрифтом, поддерживающим кириллицу. Отдельный Python/Matplotlib контейнер не нужен.

Render cache key:

```text
shared-render-v1/<sha256-bundle-key>/<chart>.png
```

Сейчас в SHA-256-идентификатор входит внутренний маркер
`shared-render-v19-reference-v-band-penalty-decomposition`; его изменение инвалидирует
производные изображения без переименования или дублирования ограниченного корня кэша.

## 18. Пользовательский сценарий

### 18.1. Вход

MVP равноправно принимает координаты двумя способами:

1. **Штатная отправка геопозиции:** Telegram `location` либо VK `geo` attachment. Бот показывает платформенную кнопку «Отправить геопозицию», где это поддерживается.
2. **Обычное текстовое сообщение:** `59.9386, 30.3141` или `59.9386 30.3141`. Команда `/forecast 59.9386 30.3141` поддерживается как дополнительный, но не обязательный синтаксис.

Оба способа после разбора дают один и тот же `Location` и проходят одинаковый pipeline. Бот подтверждает распознанные широту/долготу и найденную timezone до либо вместе с результатом.

Названия городов и адреса в MVP не разбираются: адресный геокодер был бы отдельной внешней зависимостью и неоднозначным источником координат.

### 18.2. Обработка

1. Platform adapter превращает update в общий `bot.Update`.
2. Валидируются координаты и синтаксис команды.
3. Определяется локальная timezone.
4. Router выбирает providers и совместимые runs.
5. Проверяется render cache.
6. При cache miss извлекается/читается point cache.
7. Выполняются нормализация, расчёты и renderer.
8. Сначала отправляется краткая сводка модели/freshness/засветки, затем семь последовательных вложений: три больших графика как документы и четыре меньшие диагностики как фотографии.
9. Общий handler вызывает небольшой messenger-интерфейс, реализованный активным platform adapter.

### 18.3. Текстовый контракт ответа

```text
ICON-EU 2026072206 UTC
SynScan: долгота 030°19′ E, широта 59°56′ N
Актуальность данных: 7 ч 59 мин
Период: 22.07 09:00 — 25.07 09:00
Сетка: ICON-EU 0.0625°
Модельная высота поверхности: … м над уровнем моря (ICON HHL).
Засветка: ориентир Бортля 8–9 (LPI …, SQM …, Light Pollution Atlas 2024).
Сравнение засветки: ориентир Бортля 8–9 (LPI …, SQM …, World Atlas 2015).
```

Координаты SynScan формируются из исходной пользовательской точки, а не из
выбранного узла ICON. Пульт запрашивает сначала долготу, затем широту; значения
округляются до ближайшей поддерживаемой им угловой минуты с явным указанием
полушарий `E/W` и `N/S`.

Платформенные ограничения длины и числа вложений решаются только в адаптере. Бизнес-текст и графики общие.

## 19. Кэширование, очередь и конкуренция

- point cache привязан к реальному модельному узлу, а не округлённой пользовательской координате;
- render cache привязан к модельному run, точным координатам и версиям алгоритма/renderer;
- один point bundle содержит ветер, поверхность и облака; три ecCodes-выборки выполняются параллельно;
- RAM LRU ограничен одновременно 512 точками и оценочным бюджетом 20 GiB; `GOMEMLIMIT=24GiB` оставляет запас ecCodes и runtime;
- одинаковые одновременные point-запросы объединяются через per-key flight;
- каждая включённая платформа имеет шесть шардированных по peer workers: разные peer обрабатываются параллельно, порядок одного peer сохраняется;
- очередь каждого adapter ограничена и при заполнении создаёт backpressure только своему poller;
- одна общая очередь обычных прогнозов ограничивает активные расчёты Telegram и VK значением `ASTRO_FORECAST_CONCURRENCY` и сообщает ожидающим место;
- «Горизонт» и астрокупол делят одну ограниченную directional FIFO ёмкостью
  `ASTRO_DIRECTIONAL_QUEUE_SIZE`; `ASTRO_DIRECTIONAL_CONCURRENCY` задаёт число
  активных тяжёлых расчётов (до измерений рекомендуется `1`), а legacy
  `ASTRO_HORIZON_CONCURRENCY=1` не влияет на production scheduling;
- ecCodes ограничен общим семафором на восемь процессов;
- публикация нового run не ломает текущий запрос: запрос держит неизменяемые ссылки на manifests выбранного bundle;
- кэш записывается `temp + fsync + rename`.
- тайлы засветки кэшируются отдельно от прогнозов; год атласа меняется только оператором, а кэш сохраняет не более двух последних лет.

Внешний Redis для одного экземпляра не даёт полезного выигрыша.

## 20. Устойчивость и fallback

| Сбой | Поведение |
|---|---|
| Новый run неполон | Остаётся предыдущий current |
| Provider недоступен | Используется последний полный run; при превышении `max_stale_age` пользователь видит явное предупреждение |
| Точка вне покрытия ICON-EU | Используется ICON Global с явным указанием модели |
| Исследовательский источник ICON-Ru недоступен | Production не затрагивается: от него не зависит ни один production adapter |
| GEOS-CF недоступен или устарел | Кольцо Reference V становится частичным/недоступным; общий прогноз ICON и Overall продолжаются без изменений |
| Часть верхних уровней отсутствует | Missing cells + сниженный confidence |
| Один график не построился или не загрузился | Отправляются сводка и все успешные графики; после попытки всех вложений сообщается о сбоях |
| Telegram недоступен | VK продолжает работать и наоборот |
| Контейнер перезапущен | Adapter получает новый long-poll cursor у своей платформы; локальный offset-файл не ведётся |
| Мало диска | Sync не стартует, удаляется disposable cache, current сохраняется |
| ecCodes вернул ошибку | Файл/run помечается invalid, ошибка не кэшируется как успешный результат |

Порог свежести задаётся отдельно для provider и управляет только предупреждением, а не выбором или удержанием cache entry. Пользователь всегда видит base time и run ID. Ключи point/render cache содержат run ID, поэтому публикация нового полного run автоматически обходит все артефакты предыдущего.

VK media upload выполняет не более трёх попыток. После ошибок adapter ждёт
`1 с`, затем `2 с` и перед повтором запрашивает новый platform upload URL.
Неполный ответ отклоняется до `photos.saveMessagesPhoto`/`docs.save`; цикл
ограничен контекстом пользовательского запроса и не применяется к
произвольным внешним доменам. Успешные исходящие сообщения VK разделены минимальным
интервалом `250 мс` внутри одного последовательного запроса. Общей
блокировки нет: параллельные VK-запросы не задерживают друг друга; ограничение
находится только в VK adapter и не влияет на Telegram.

## 22. Docker и эксплуатация на production-сервере

### 22.1. Образ

Multi-stage Dockerfile:

1. Go builder собирает статически максимально возможную часть `bot_astrosferum`.
2. Runtime OSGeo GDAL на Ubuntu содержит CA certificates, timezone data, ecCodes/CDO tools и шрифты.
3. Публичные Russian Trusted Root/Sub CA встроены только в TLS pool VK adapter; его transport разрешает лишь `vk.ru`, `*.vk.ru`, `vk.com`, `*.vk.com`, а VK API вызывается через `https://api.vk.ru`.
4. Процесс запускается не от root.
5. Публичные порты не объявляются.

Расширение российскими УЦ не устанавливается на весь контейнер. Сертификаты
вшиты в VK adapter и объединяются с системным pool только в его отдельном
transport. Redirect, upload и Long Poll URL вне `vk.ru`, `*.vk.ru`, `vk.com`,
`*.vk.com` отклоняются; проверки hostname и срока действия остаются включены.
Это лишь разрешает альтернативную цепочку, если её отдаёт сам VK, но не
создаёт замену отозванному leaf-сертификату; стандартный TLS client Go не
выполняет универсальную проверку CRL/OCSP автоматически.

Один и тот же image используется для `serve`, `sync`, `doctor` и тестового рендера.

### 22.2. Compose

Compose содержит PostgreSQL и один application service:

- `restart: unless-stopped`;
- `init: true`;
- `stop_grace_period` для завершения активных файловых операций;
- bind mounts только из текущего проекта;
- ограниченная ротация Docker logs;
- PostgreSQL healthcheck блокирует старт приложения до готовности БД;
- user UID/GID согласован с владельцем каталогов на host.

Нет зависимости от nginx и нет конфликта портов с другими сервисами production-сервера.

### 22.3. Backup

Нужно резервировать:

- `docker-compose.yml`, конфиг и source repository;
- закрытые secret-файлы через существующий секретный backup process;
- при появлении пользовательских настроек — `data/state`.

Скачанные GRIB, point cache и PNG cache восстанавливаются автоматически и в обязательный backup не входят.

Runtime автоматически сохраняет только два модельных run, до 512 point bundles на каждый, до 256 render bundles не старше 48 часов и три Docker log-файла по 10 MiB. Временные файлы кешей старше часа удаляются при старте и очередной записи. GRIB остаются на диске, а Linux page cache использует свободную RAM без второй копии и без отдельного tmpfs.

## 23. Наблюдаемость

Структурированные события:

- `sync_started`, `sync_completed`, `sync_failed`;
- provider, run ID, bytes, duration, file counts;
- `request_received`, `request_completed`, `request_failed`;
- platform, coarse region, cache hit/miss, durations этапов;
- current run age и free disk;
- очередь и число активных workers.

Не логируются bot tokens, полный update payload, текст личных сообщений и точные пользовательские координаты. Для диагностики координаты заменяются grid cell ID либо грубым регионом.

`doctor` проверяет:

- чтение config и secret-файлов;
- доступность записи в `data`;
- наличие и версию ecCodes;
- свободный диск;
- валидность current manifests;
- свежесть providers;
- возможность построить небольшой fixture-график.

## 24. Безопасность и приватность по умолчанию

- контейнер работает без root и без Docker socket;
- нет опубликованных TCP-портов;
- tokens только в `secrets/`, `0600`, исключены из Git;
- исходящие HTTP-запросы имеют timeout и лимиты размера;
- platform long-poll cursor предотвращает обычный повтор событий внутри работающего процесса;
- ограниченные peer-affine очереди каждой платформы не позволяют бесконечно накапливать запросы в процессе;
- входные координаты и команды ограничены по длине и диапазону;
- `os/exec` получает аргументы отдельным массивом, пользовательский ввод не проходит через shell;
- скачанный GRIB валидируется до публикации;
- точные координаты попадают в постоянные пользовательские записи только по явной команде сохранения. Несохранённые координаты могут временно оставаться в ограниченных render caches, включая текст координат внутри сгенерированных PNG, но эти артефакты не содержат user ID и удаляются по правилам retention;
- debug-ответы не содержат путей, токенов и внутренних команд.

## 26. Этапы реализации

### Этап 0 — обязательный data-source spike

Текущие измеренные результаты и оставшиеся проверки объединены в [научной методике](scientific-method.ru.md#6-контракты-источников-данных-и-проверка-на-сервере). Для ICON-EU проверены field keys, domain, объём и длительность полного актуального run; для ICON Global проверены pressure, surface, model-level cloud/PBL данные и native-grid point extraction через CDO; discovery metadata и topic ICON-Ru получены. Остаются фактическая WIS notification и наблюдательная калибровка.

1. Скачать минимальный полный fieldset ICON-EU и зафиксировать реальные filenames/GRIB keys.
2. Проверить, что открытый домен содержит Санкт-Петербург и Москву.
3. Сверить model levels `U/V/T/P/QV/TKE/HHL`, surface fields, единицы и задержку публикации.
4. Скачать и проверить эквивалентный набор ICON Global для fallback и baseline. Выполнено для pressure, surface, cloud/PBL и HHL.
5. Подключиться к публичному WIS 2.0 потоку ICON-Ru для shadow verification.
6. Измерить размер run, скорость загрузки и время `grib_get -l` на production-сервере.

Критерий выхода: сохранён fixture и таблица «требуемое поле → реальный GRIB key/source». Без этого нельзя честно фиксировать формулу seeing-v1.

### Этап 1 — вертикальный slice

- Go module и config loader;
- основной provider ICON-EU;
- ручной `sync` одного срока;
- extraction одной точки;
- семь PNG из fixture;
- `doctor`.

### Этап 2 — полноценные данные

- атомарные runs и scheduler;
- ICON Global fallback adapter (реализован);
- исследование источника ICON-Ru WIS; shadow adapter остаётся в плане;
- domain-based provider routing и единый-provider bundle;
- point/render cache;
- weather/dew/seeing/conditions-v8-precip-veto-penalty-decomposition.

### Этап 3 — боты

- общий request/response contract;
- Telegram adapter;
- VK adapter;
- независимые retry supervisor, bounded worker queues, native location conversion и media upload.

### Этап 4 — production

- Dockerfile/Compose;
- deploy в `/opt/docker/bot-astrosferum`;
- `doctor`, PostgreSQL healthcheck и log rotation;
- проверка рестарта и восстановления после неполного sync;
- лимиты диска и run retention.

## 27. Критерии готовности MVP

- одна и та же координата даёт эквивалентный результат в Telegram и VK;
- для Санкт-Петербурга и Москвы весь production bundle берётся из ICON-EU, пока локальная верификация не обосновала иную политику;
- вне доступного ICON-EU domain используется ICON Global;
- ICON-Ru WIS не влияет на production, поскольку shadow adapter пока не реализован;
- источник, сетка и run отображаются пользователю;
- погода, роса и туман видны на первом графике;
- строятся weather PNG `3200×1080`, Overall PNG `4320×1600`, облачный PNG `3200×1100` и четыре читаемых PNG `1280×960`;
- seeing называется прогнозным индексом и содержит confidence;
- неполный run не публикуется;
- после рестарта сохраняются current model manifests, а platform cursors заново запрашиваются у API;
- токены отсутствуют в Git и логах;
- все bind mounts бота/worker находятся под `/opt/docker/bot-astrosferum`;
- при недоступности одного platform API второй бот продолжает работать;
- приложение не публикует TCP-порты на host.

## 29. Опциональный анализ горизонта для ICON-EU

### 29.1. Продукт и граница provider

Анализ горизонта — опциональное действие второго этапа после обычного прогноза
из семи графиков. Он сравнивает восемь фиксированных азимутов
`С, С-В, В, Ю-В, Ю, Ю-З, З, С-З` при опорном геометрическом угле возвышения
`10 deg` для каждого
доступного почасового срока 72-часового периода ICON-EU. Результат — одна
компактная heatmap «время × направление» и summary; обычные погодные графики
повторно не строятся.
Локализованная кнопка показывает настроенную оценку по измерениям, например
`Горизонт (~3 мин)`; это ориентир очереди, а не timeout задачи.

Действие намеренно доступно **только для ICON-EU**. Кнопку можно показывать,
только если одновременно выполнены условия:

- feature flag включён;
- provider обычного прогноза — именно ICON-EU;
- для периода есть pressure, surface, cloud и HHL одного неизменяемого run без
  экстраполяции между run;
- наблюдатель и каждая фактическая точка луча остаются внутри опубликованного
  покрытия ICON-EU.

В ответе ICON Global кнопки «Горизонт» нет, Global-задача анализа не существует,
синтетической замены тоже нет. Callback payload нельзя считать доверенным: он
может быть подделан или устареть. Поэтому workflow повторно проверяет подписанный
контракт provider/run/координат, заново строит фиксированный период и footprint,
а cache key выводит из текущих версий алгоритмов. Если текущий run сменился,
пользователю предлагается построить новый обычный прогноз; смешивать run нельзя.

### 29.2. KISS-границы пакетов

Расширение сохраняет существующее направление зависимостей:

```text
Telegram callback ----+
                      +--> internal/app/bot: action и Horizon job workflow
VK message_event -----+                  |
                                         +--> internal/model/iconeu: batch snapshot
                                         +--> internal/forecast: расчёт
                                         +--> internal/render: компактный PNG
```

- `internal/app/bot` отвечает за versioned action route, сбор почасового периода, lifecycle
  задачи, дедупликацию, cache policy, локализацию и доставку;
- `internal/model/iconeu` читает один закреплённый run/период и возвращает
  нормализованный provider-neutral snapshot; формул индекса и user flow в нём нет;
- `internal/forecast` содержит сферическую геометрию и все физические и
  инженерные расчёты по направлениям; он не импортирует model adapter или platform;
- `internal/render` превращает готовый результат в одно детерминированное
  изображение и не обращается к сети;
- Telegram и VK остаются равноправными transport adapters. В них нет научных
  формул Horizon, очереди или импорта другого адаптера;
- `cmd/bot_astrosferum` остаётся composition root и при включённой функции
  создаёт один общий Horizon workflow для обеих платформ.

Общий callback envelope версионирован и ограничен общим для платформ лимитом
Telegram `callback_data`. Horizon использует явный action ID `horizon.v1`;
compact payload аутентифицирован постоянным HMAC-ключом с mode `0600`, но всё
равно сверяется с текущим состоянием модели. Этого достаточно для будущих
действий без message broker, Redis, нового сервиса или второго bot handler.
Контракт callback следует [Telegram Bot API](https://core.telegram.org/bots/api),
а VK payload нормализуется в то же application action.

### 29.3. Полный почасовой период одного неизменяемого run

Heatmap использует фиксированный интервал `f000..f072` неизменяемого ICON-EU
run: 73 почасовых срока на 72 часа, а не один выбранный «лучший» час. Все
восемь направлений имеют строго одинаковую шкалу времени. День,
светлые сумерки (`0…−12°`), астрономические сумерки и ночь выделяются в рассчитанных субчасовых позициях;
полярный день остаётся валидным, явно дневным периодом, а не включает
специальный selector. Подпись содержит run, его текущую актуальность и полный
интервал valid time, поэтому уже прошедшие ранние сроки остаются явными.

Model adapter закрепляет весь период за одним ICON-EU run. Он пакетно читает
все нужные pressure-level `U/V/T/Z` steps, все почасовые surface, cloud, TKE,
MH и visibility steps и общую HHL geometry по всем lookup cells. Трёхчасовые
исходные pressure variables линейно интерполируются на почасовую сетку только
между соседними сроками того же run; HMNSP/TKE, `Cn2`, seeing, `tau0` и индекс
после этого пересчитываются и сами никогда не интерполируются. Экстраполяции
дальше `f072`, через отсутствующий край или границу run нет. Координаты одной ячейки output-grid `0.0625 deg`
дедуплицируются. CDO сразу выводит таблицу; промежуточные GRIB-копии не хранятся.
Формулы и ограничения описаны в
[разделе Horizon научной методики](scientific-method.ru.md#7-анализ-условий-у-горизонта-по-направлениям).

Run identity проверяется до любого cache reuse или тяжёлой работы. Источник
сверяет тот же current run до и после acquisition, workflow проверяет его снова
после расчёта/render, а delivery workers — непосредственно перед каждой
отправкой, включая cache hit. Если появился новый run или текущий run нельзя
подтвердить, PNG не отправляется, а пользователю предлагается запросить новый
обычный прогноз. Caption строится в момент отправки с настроенным для ICON-EU
`max_stale_age`, поэтому свежесть нового и кешированного результата оценивается
одинаково.

### 29.4. Изолированный класс тяжёлых направленных расчётов

Horizon и астрокупол не должны занимать workers обычного точечного прогноза.
Текущая production-композиция реализует следующую границу:

- одна ограниченная directional FIFO ёмкостью `ASTRO_DIRECTIONAL_QUEUE_SIZE`
  общая для запросов «Горизонта» из Telegram/VK и запросов астрокупола из web;
  активный лимит задаёт `ASTRO_DIRECTIONAL_CONCURRENCY` (`1..32`, до измерений
  рекомендуется `1`);
- один изолированный HTTP worker service обслуживает оба вида расчёта; его
  concurrency guard соблюдает тот же лимит слотов, а process-shared slot leases
  в `data/state/run-leases` ограничивают суммарную работу случайных
  дополнительных реплик worker и операторского CLI `render-horizon`;
- старое значение `horizon_analysis.concurrency` /
  `ASTRO_HORIZON_CONCURRENCY` осталось только как совместимое ограничение
  конструктора; после подключения coordinator локальные расчётные workers
  «Горизонта» не запускаются;
- общий лимит CDO под управлением `horizon_analysis.cdo_workers`: validation
  принимает `1..16`, production по умолчанию допускает восемь subprocesses.
  Horizon создаёт один неизменяемый план
  весов на запрос и переиспользует его для всех bundle, а предзагрузка
  астрокупола применяет один такой план к параллельно извлекаемым нативным
  срокам;
- два delivery workers и отдельная bounded delivery queue с ограниченным
  admission для cache-hit upload, чтобы медленная отправка на платформу не
  создавала неограниченный backlog goroutines или памяти;
- немедленный ответ на callback, затем позиция в очереди и честная примерная
  длительность;
- не более одной активной задачи на platform/user identity, трёхсекундная
  защита от повторного нажатия и fan-out одинаковых job keys, ограниченный
  `max(32, queue_size*32)` waiters;
- timeout задачи и cancellation context принадлежат background workflow, а не
  короткому callback request;
- workers, семафор и timeout обычного прогноза остаются независимыми.

Каждая таблица CDO нормализуется сразу после завершения bounded subprocess, после
чего raw table освобождается; до расчёта сохраняется только нормализованный
результат из 73 frames. Жёсткий Compose-лимит directional worker задаётся
`ASTRO_DIRECTIONAL_WORKER_MEMORY_LIMIT` (`24g` по умолчанию), а более низкая
цель Go heap — `ASTRO_DIRECTIONAL_WORKER_GOMEMLIMIT` (`12GiB` по умолчанию).
Ни одно значение не является научной константой. Изменение допускается только
после измерения peak RSS в полном smoke-расчёте с запасом для CDO, PostgreSQL и
page cache host. В частности, увеличение directional concurrency умножает
возможный resident footprint астрокупола и требует повторной проверки cgroup-
лимита worker и disk admission всего проекта.

Достаточно ограниченной in-process очереди coordinator и изолированного
синхронного worker. Незавершённая задача не переживает рестарт: пользователь
может повторить её, а уже опубликованная атомарная запись disk cache
сохраняется. Для одного класса опциональных расчётов это проще и честнее, чем
отдельная database-backed job system.

### 29.5. Кэш и очистка

Horizon cache отделён от обычных point/render caches. В identity входят E5
координаты, округлённый HHL наблюдателя, provider и run ID, фиксированное окно
`window=f000-f072-hourly`, версия Horizon algorithm, фиксированные параметры
геометрии, полная калибровка, общая с Overall (параметры `ASTRO_OVERALL_*` и
`ASTRO_CLOUD_*`), версия renderer algorithm и язык. Поэтому изменение
калибровки создаёт новый key, а не переиспользует старый результат. Из key
material строится hash для пути, поэтому исходные координаты не попадают в
имена файлов или логи. Cache hit допустим только для точно того же
неизменяемого run и контракта.

Научный маркер — `horizon-spherical-los-tke-hmnsp99-v7`, кэш приложения
schema — `horizon-cache-v2-interactive`. Изменение формулы или serialized/rendered contract
требует смены соответствующего marker.

PNG и metadata публикуются через staging и atomic rename. Хранение ограничено
жёстким TTL от `CreatedAt` и числом записей; mtime используется только для LRU,
поэтому cache hit не продлевает жизнь. Очистка выполняется при создании кеша,
после публикации и периодически с интервалом `min(cache_ttl/4, 1h)`, пока
работает heavy worker. Допущенный к отправке готовый PNG получает временную
hard-link `.lease-*`: удаление его keyed-каталога не ломает уже начатый upload,
а delivery worker удаляет lease после попытки. При старте удаляются брошенные
`.incoming-*` и `.lease-*`; ошибки очистки возвращаются или логируются, а не
считаются успехом. Текущие defaults ветки разработки — 48 часов и 128 записей.
Runtime cache и temp остаются под существующим volume `data/` и исключены из
Git. PNG содержит отображаемые координаты с четырьмя знаками после запятой, но
кеш не связывает их с user ID. В логах допустимы run ID, период/число сроков,
число точек, длительность и безопасный класс ошибки, но не callback payload,
user ID или точные координаты.

### 29.6. Эксплуатационный gate

Ветку нельзя называть развёрнутой, пока не пройдены все локальные проверки,
один реальный расчёт ICON-EU и отрицательный тест ICON Global, доказывающий
отсутствие и кнопки, и запускаемой задачи. После deploy обязательны `doctor`,
проверка startup logs, обычный прогноз, кнопка/action «Горизонт» и измерение
обычного прогноза во время параллельной Horizon-задачи. Провал любого gate
требует остановить или откатить deploy и отправить отчёт об ошибке вместо
сообщения об успехе.

## 30. Атмосферный астрокупол ICON-EU

### 30.1. Контракт продукта

Астрокупол — асинхронный направленный атмосферный продукт. Он содержит до 72
последовательных нативных сроков, кратных
часу. Свежий цикл обычно даёт все 72 кадра; для стареющего цикла окно
заканчивается перед первым разрывом нативной почасовой сетки без интерполяции
готовых направленных величин.
Внешняя окружность — **граница расчёта 10°**, а не геометрический горизонт;
меньших высот в контракте нет. В каждом профиле ровно один узел `90°` с
`azimuth=null`.

Основной неизменяемый угловой профиль — `production-v2`: восемь колец на
высотах `10/20/30/40/50/60/70/80°`, по 16 азимутов с шагом `22,5°`, и один
общий зенит. Это `8 × 16 + 1 = 129` узлов на срок и `72 × 129 = 9 288`
узло-часов. Исторический `dense-v1` с 353 узлами сохраняется только как
версионированный legacy/reference-контракт и не является production-сеткой.
При дисковом ограничении остаётся отдельно версионированный
`sparse-storage-v1`: 16 азимутов на `10/20/30/45/60/75°` плюс зенит — 97
узлов на срок.

Профиль выбирается один раз до допуска задачи и не разрежается внутри набора.
Решение `DiskBudget` относится к полноте исходного хранилища: полный `dense`
volume отображается в расчётную сетку `production-v2`, а ограниченный `sparse`
volume — в `sparse-storage-v1`. Если даже sparse не сохраняет резерв места и
inode, публикация закрывается с ошибкой. Payload и геометрия браузера содержат
точные profile, версию геометрии и SHA-256 digest описателя.

### 30.2. Границы науки и источника

Астрокупол доступен только для полного неизменяемого run ICON-EU. Кнопки и
синтетической замены для ICON Global нет. Model adapter отвечает за получение
и реконструкцию исходных полей; `internal/forecast` — за геометрию, рефракцию,
физические интегралы, замыкание облаков и Overall. В web, Telegram, VK и
renderer научных формул нет.

Интерполировать разрешено только исходные метеорологические переменные в
пространстве модели и во времени. Затем каждый луч проходит полный нелинейный
пересчёт. Готовые сиинг, `tau0`, пропускание облаков, Horizon/Sky/Overall и
детерминированное качество явно запрещены как вход интерполяции. Прямой луч и
полная рефракция Ciddor имеют разные версии; последняя интегрирует связанную
ECEF-систему луча в восстановленном трёхмерном поле показателя преломления.
Формулы и численные допуски приведены в
[научной методике](scientific-method.ru.md#8-полный-астрокупол).

Физические точки разбиения являются исходными данными пути, а не случайным
результатом адаптивной квадратуры. Текущие идентификаторы —
`astrodome-science-path-v23` и
`astrodome-science-kernel-v29`. Максимальный радиус локализации корня
физического или горизонтального события равен 0,2 мм. Побитово идентичные
представленные координаты `pathM` образуют одну составную геометрическую точку
разбиения, даже если идентификаторы событий различаются; сохраняется их
упорядоченное объединение, и все связанные переходы применяются в этом
сечении. Побитово различные координаты не усредняются и не объединяются:
кандидаты на расстоянии не более 0,4 мм приводят к отказу. Запас стороны равен
0,5 мм, масштаб общего рекурсивного доказательства — 0,2 мм, а проверяемая
оболочка вычисления положения и координат остаётся равной 1 мм. Номинальный
нуль с плавающей точкой сохраняется как интервал
остатка; любой неразрешённый лист отклоняет весь узел. Номинального
микрометрового представителя разбиения и preview-переопределения допусков нет.
Ошибка одного узла обычно изолируется как явная ячейка `unavailable`, а
не уничтожает остальные рассчитанные направления и сроки. Единственное
продуктовое исключение — описанное ниже версионированное приближение короткого
пути; оно публикуется как `limited`, но не как полностью сошедшееся. Кадр без единого
пригодного узла по-прежнему отклоняется и не попадает в кеш результатов. У
незавершённого или заблокированного рельефом преломлённого луча
`direction_at_model_top_ecef=null`: worker не изготавливает касательную на
границе модели, которой луч не достиг. Для каждого доступного преломлённого
узла касательная остаётся обязательной.

Интегратор рефракции `dormand-prince-5-4-event-v3` в production принимает луч
только после согласования двух последовательно уточнённых прямых проходов.
Дополнительный обратный проход и проверка обратимости выполняются только в
reference-режиме для калибровки, регрессии и release verification. Принятый
плотный полином DOPRI Шампина публикует динамическую границу ошибки
вычисления декартового положения и производной по сумме модулей формирующих
слагаемых. Это граница вычисления принятого полинома, а не ошибки усечения ОДУ,
глобального согласования прямых проходов или метеорологической
неопределённости. Для ошибок положения и производной в точке используются
раздельные суммы модулей мономов по X/Y/Z, проверенная оболочка `gamma128` для
каждой компоненты и округлённое наружу евклидово объединение. Более длинные
пути формирования и ограничения полиномов Бернштейна для границ производной
и ускорения сохраняют отдельную оболочку `gamma1024`. Каждое вычисление
горизонтального корня, физическая проба и
средняя точка метрической оценки переводят ошибки плотного положения,
сферических координат, нормированной сетки и привязки к линии сетки в одну
эквивалентную ошибку положения и проверяют жёсткий предел 1 мм. Принятые
остатки используют меньшие фактические ошибки, а не этот потолок:
ECEF-предикаты сетки получают границу плотного положения; билинейные
предикаты — зависящую от поля неопределённость из границ долей
широты/долготы и разностей противоположных рёбер именно этого поля; остатки
HHL/PBL/облачных границ складывают ошибку высоты луча с неопределённостями
фактически входящих в границу операндов. Нелинейный fallback 200 гПа
распространяет координатные интервалы четырёх исходных полей высоты/давления и
отдельно добавляет оболочку арифметики логарифмов, деления и высоты.
Учитывающая единицы оболочка binary64 по исходным сокращающимся операндам
остаётся отдельным членом.

Переключатель публичного доступа не выбирает научную сетку. Доступ
администратора при выключенном публичном rollout и обычный публичный доступ
используют одно решение `DiskBudget`: полный dense-volume рассчитывается на
`production-v2`, а `sparse-storage-v1` выбирается только при необходимости по
объявленному дисковому бюджету. Принудительного sparse-preview для
администраторов нет.

Горизонтальные границы ячеек изолируются непосредственно в ECEF по предикатам
$y\cos\lambda_b-x\sin\lambda_b=0$ и
$z\cos\phi_b-\sqrt{x^2+y^2}\sin\phi_b=0$; равенство округлённых `atan2` или
`asin` не используется как предикат корня. В метрических сертификатах и
оценках кривизны граница скорости по Бернштейну заменяется на
$U=\max\{1,U_B\}$. Положительные нижние границы
$\rho=\sqrt{x^2+y^2+z^2}$ и $p=\sqrt{x^2+y^2}$ выводятся непосредственно из
средней точки ECEF, динамической границы вычисления плотного полинома и
$U\Delta s/2$. Цилиндрический радиус не восстанавливается как
$\rho\cos\phi$.

Кандидатные линии сетки перечисляются по округлённой наружу границе угловой
достижимости на каждом принятом интервале DOPRI; знаки в концах не служат
фильтром, короткий интервал не пропускается молча. Корни широты и долготы
сохраняются как отдельные сертифицированные скобки. Они образуют единый угол
сетки только при точном нуле обоих предикатов в одной и той же координате
пути; пересекающиеся конечные скобки не объединяются. Траектория, для которой
нельзя доказать сторону из-за следования вдоль линии сетки или нахождения в её
численной оболочке, пока недоступна. Поддержка этого редкого случая требует
явного будущего контракта владения двумя ячейками с объединёнными границами
производных; простой обход проверки ячейки был бы научно некорректен.

Решения WMO по вертикальному градиенту по-прежнему используют единый
компенсированный остаток
$R=\Delta z+500\,\mathrm{м\,К^{-1}}\Delta T$ и одинаковый порядок операций
binary64 в планировщике и ядре. Доказательства достижимости перечисляют только
те предикаты, которые действительно может прочитать дискретный алгоритм WMO.
Гладкие границы HHL, полных уровней, поверхности, облачных ярусов и билинейные
предикаты WMO сохраняют сертификат трансверсальности по секущей и кривизне.
На пропущенных участках у границы горизонтальной ячейки предикаты HHL, полных
уровней, облачных ярусов и исходных билинейных ограничений PBL могут
дополнительно перенести оболочку производной с соседнего внутреннего интервала
с помощью сертифицированной границы второй производной. Если ни проверка
Липшица, ни односторонняя производная не исключили корень, v23 учитывает только
пропущенную краевую полосу в ограниченном метровом бюджете, сохраняя полный
поиск корней во внутренней сертифицированной области. PBL получает полный сертификат корня
только после доказательства одной ветви
`clamp(MH,500 м,2000 м)` на всём интервале. В смешанной ячейке планировщик
строго изолирует корни исходных билинейных решений `MH-500 м` и `MH-2000 м`,
делает их доказательные скобки обязательными концами, доказывает одну ветвь в
каждом полученном разделе и только затем изолирует гладкую поверхность PBL.
Неопределённые или пересекающиеся свидетельства ветвей приводят к отказу.
Если верхнее ограничение делает границу PBL точно равной верху нижнего
облачного яруса `HSURF+2000 м`, общий набор нулей регистрируется один раз.
Контракт пути v23 сохраняет введённую в v22
алгебраически обоснованную единственную регистрацию общего набора нулей
`mean-lapse(lower, upper=lower+1)` и мгновенного градиента.

Путь v23 сохраняет введённый в v22 сжимающий оператор (contractor) монотонного корня,
существование и единственность которого уже доказаны строгими противоположными знаками
интервалов остатка в концах и не содержащей ноль оболочкой производной. Он
сохраняет этот исходный сертификат и отдельную скобку корня, после чего
пересекает её с округлёнными наружу образами защищённого интервального метода
Ньютона $I\cap(x-F(x)/D)$ в концах и середине. Если сокращения в середине
недостаточно, до исчерпания бюджета уточнения обязательно проверяются парные
внецентровые пробы по обе стороны центрального окна. Строгий знак интервала
остатка может дополнительно сократить соответствующую монотонную сторону;
интервал, содержащий ноль, никогда не получает знак по номинальному значению.
Отсутствие сокращения или непреодолимый информационный предел по-прежнему
приводят к отказу. Для приёмки обе округлённые наружу полуширины от фактически
представленной середины всё так же должны быть не больше 0,2 мм; порог разных
корней 0,4 мм и запас стороны 0,5 мм не изменены. Исторический полный прогон
v25/path-v21 завершил 9 029 из 9 030 узло-часов; единственной недоступной
ячейкой был именно этот PBL-случай. В целевом production-повторе v26/path-v22
предзагрузка 150 колонок заняла 180,744 с, а ячейка стала доступна после
1,068-секундного расчёта узла. Этот исторический целевой результат не заменял
полный прогон; историческое измерение v28/path-v22 отдельно приведено ниже.

Нелинейная резервная поверхность 200 гПа восстанавливается из исходных полей
давления и высоты через устойчивые к сокращению отношения `log1p`. Полная
ошибка цепочки давление/логарифм/деление/высота округляется наружу и добавляется
к каждой пробе остатка. Если логарифмический знаменатель не отделён от своей
арифметической ошибки либо ошибка восстановленной высоты превышает
1-миллиметровый порог вычисления положения и координат, узел закрывается с
ошибкой. После этого границы первой и второй производных допускают тот же
сертификат единственности по секущей и кривизне без интерполяции готовой
резервной высоты.

Запас стороны 0,5 мм задаёт строгие пределы, зависящие от типов концов:
`0,001000000000001… м` для двух физических концов,
`0,0005000000000005… м` для одного физического и `0,01 м` для двух численных
адаптивных концов. Следовательно, 1 мм — обычный атомарный предел для двух
физических концов без `CertifiedShortInterval`; ветка короткой панели с
доказательством вместо него использует свой сертифицированный открытый
безопасный интервал. Границы стандартных
правил равны
$L_{GL2,\min}=0{,}002366025403786804672\ \mathrm{м}$,
$L_{GL3,\min}=0{,}004436491673108144934\ \mathrm{м}$,
$L_{GL5,\min}=0{,}010658690662000389306\ \mathrm{м}$ и
$L_{K15,\min}=0{,}11703258434509156429\ \mathrm{м}$. Ядро v29 использует
независимые GL2/GL1, GL3/GL2 и GL5/GL3 между последовательными границами и
G7/K15 выше границы K15; дочерний интервал с двумя численными концами всегда
использует G7/K15. При $L_{GL2,\min}<L$ применяется GL2/GL1. На границе GL2
или ниже v29 может применить положительную одноточечную формулу средней точки
только когда три безопасные внутренние пробы остаются в одном доказанном
разделе. Суммарный учёт равен сумме длин таких панелей и длине объединения
допущенных краевых полос; ровно 1 м допустим, превышение отклоняется. Результат
получает `data_quality=limited`, `quadrature_convergence=0`, ненулевой
`approximation_length_m` и причину `short_path_approximation`. Ядро v29 сохраняет удаление прежнего согласованного по моментам пути Q5/Q3: запасы концов
могли сделать его знакопеременные веса сколь угодно плохо обусловленными, а
точное вычисление коэффициентов не ограничивало ошибку нелинейной
подынтегральной функции. Все выбранные разности старшего и младшего правил
остаются инженерными оценками, а не строгими оболочками ошибки усечения.

Каждая обычная, неограниченная панель проходит покомпонентную проверку
«абсолютный плюс относительный допуск», после чего накопленные встроенные
ошибки таких панелей должны вместиться в один общий бюджет того же вида.
Ограниченная панель средней точки вместо этого публикует явный инженерный
допуск и сообщает об отсутствии сходимости. Неподтверждённые отрицательные оценки физически
неотрицательных компонентов приводят к отказу; округлить до нуля можно только
значение, чей модуль покрыт его оценкой ошибки. Production v29 публикует
накопленную встроенную оценку старшего/младшего правила без второго полного
атмосферного прохода. Независимый повтор с половинными допусками и одноразовым
делением исходных атомарных интервалов включается только в reference-режиме для
регрессии, калибровки и release verification. Любое несовпадение сигнатуры
разбиения в этом режиме приводит к отказу: путь v23 обязан сертифицировать
исходные точки WMO до интегрирования, ядро их автоматически не делит. Готовые
сиинг, `tau0`, пропускание облаков и Overall не интерполируются.

Покрытие облаками не оценивается только по узлам квадратуры. Для каждой точно
определённой активной вертикальной опоры CLC реконструктор берёт максимум
исходного CLC по четырём столбцам горизонтального шаблона, концам исходной
временной скобки и только активной соседней паре полных уровней (либо одному
уровню постоянного продолжения сверху или снизу). Выпуклость временного,
билинейного горизонтального и вертикального восстановления превращает этот
максимум в верхнюю оболочку; перед ограничением диапазоном `[0,1]` в неё
наружу входят `nextUp`, положительное превышение суммы представленных
горизонтальных весов над единицей и `256·2^-53`. Покрытие блока равно максимуму
таких атомарных оболочек внутри одной пары «ячейка, ярус». Идентификатор
вертикальной опоры входит в сигнатуру разбиения и ключ кеша; сертификаты
поставщика для каждого перехода исходного полного уровня и предиката WMO
обязательны, любое несовпадение приводит к отказу. Оболочка консервативна по
активному исходному шаблону, но не берёт максимум по всему ярусу или столбцу
атмосферы.

Ядро v29 хранит эту оболочку отдельно от выборочного восстановленного CLC.
Каждый блок `(исходная горизонтальная ячейка, ярус AGL)` накапливает собственные
жидкую и ледяную оптические толщины и их встроенные численные допуски.
`cloud_transmission_nominal` использует восстановленные значения CLC и
номинальные толщины блоков; `cloud_transmission_conservative` — оболочку
исходных опор и `tau_block + error_block`. Совместимое поле
`effective_cloud_transmission` равно консервативному значению, и только оно
входит в направленный Overall. Точный нуль обрабатывается до логарифма, для
остальных блоков произведение накапливается через `log1p(T-1)`.

Прежние масштабы 50/100/125 мкм и примеры сантиметровых панелей являются
только историческими свидетельствами ошибки и не действуют как текущие пороги
приёмки. В частности, исторические панели `0,0251479956 м` и `0,0181762987 м`
выше исторического 5-миллиметрового предела двух физических концов в v24 и не
отклонялись в v24 только из-за своей длины. Завершённые регрессии
v25/path-v21 сохраняют
отдельными физические интервалы 1,53107653; 1,9401; 3,7474; 3,9203;
4,802253; 15,9325455; 26,7341866;
31,1486803; 41,5455627 и 48,78 мм и отдельно
проверяют объединение точно одновременных событий. Документация не
утверждает успешное завершение полного рабочего smoke-теста. Численная
политика не меняет ни **максимум 72 последовательных нативных почасовых кадра прогноза**, ни **ровно 96 часов
обычного хранения** в пользовательском каталоге; полные формулы приведены в
научной методике (A26b)–(A28i).

Основной synchronizer остаётся единственным загрузчиком и издателем. Dome
augmentation переиспользует совпадающие неизменяемые файлы base-run и получает
только недостающие полно- и полууровневые primitives. Перед физическим расчётом
worker сверяет метаданные регулярной HHL-сетки GRIB с неизменяемым манифестом,
строит цели только по точным целочисленным индексам исходной сетки и один раз
создаёт CDO `gennn`-план сбора колонок. Созданный SCRIP-файл обязан доказать
один точный адрес исходного узла, ожидаемый адрес цели и побитово точный
единичный вес для каждой цели. Каждое обрабатываемое сообщение GRIB должно
воспроизвести геометрию и порядок сканирования доказанного HHL-источника.
Координаты луча не передаются в CDO:
единственная научная горизонтальная интерполяция — собственная четырёхточечная
билинейная реализация. Канонический план исходных индексов сохраняется как
`source_column_plan_digest`; read-only weights переиспользуются во всех
`remap`-вызовах. Worker не меняет `current`: model
store `/app/data/models` доступен ему только для чтения, а запись разрешена
лишь в общий directional workspace, каталог process-shared leases и собственный
временный каталог. Публикацией результата по-прежнему владеет bot coordinator.

### 30.3. Очередь, кеш и изоляция отказов

«Горизонт» и астрокупол делят одну ограниченную FIFO. Запросы с одинаковой
расчётной identity получают один общий результат, а не дублируют работу.
Вместимость задаёт `ASTRO_DIRECTIONAL_QUEUE_SIZE`, лимит выполняемых задач —
`ASTRO_DIRECTIONAL_CONCURRENCY` (`1..32`; до измерений рекомендуется `1`).
Старое поле concurrency «Горизонта» осталось совместимой границей конструктора
и не влияет на production scheduling. Обычные прогнозы Telegram/VK имеют
независимый лимит и не зависят от готовности directional worker.

Bot coordinator владеет admission, отменой, ownership, проверками текущего run
и identity кеша. Изолированный worker только синхронно выполняет тяжёлый
расчёт. Внутренний HTTP-запрос аутентифицирован и называет заранее созданный
workspace внутри разрешённого корня; model/result bytes через bot не
проксируются. Crash, timeout или OOM worker переводит направленную задачу в
ошибку, но не останавливает синхронизацию модели и обычные прогнозы.

Настроенный лимит активных задач намеренно обеспечивается на трёх уровнях:
coordinator запускает `ASTRO_DIRECTIONAL_CONCURRENCY` потребителей FIFO, HTTP
handler worker допускает столько же запросов суммарно для обоих видов, а
context-aware N-slot `flock` gate в `data/state/run-leases` действует между
процессами worker и `render-horizon`. При завершении процесса kernel освобождает
lock, поэтому восстанавливать stale PID-файл не требуется. Случайные
дополнительные реплики worker или операторский CLI не могут поднять суммарное
исполнение выше настроенного лимита. Вместимость очереди независимо задаёт
`ASTRO_DIRECTIONAL_QUEUE_SIZE`; она не определяет число выполняемых задач.

Завершённые не зависящие от языка datasets сжимаются gzip и публикуются
атомарно. Identity включает координаты, run и digest manifest, 72-часовое окно,
grid/digest, primitive contract, версии геометрии/рефракции/science и
калибровку. Схема расчётного запроса v3 также связывает версию science path,
контракт видимого направления и SHA-256 полной настроенной научной калибровки;
тот же digest сохраняется в dataset. Узкий идентификатор
`astrodome-dataset-writer-v2` также входит в ключ
расчётного кеша: исправление writer принудительно пересоздаёт payload, не
выдавая его за новую научную формулу или схему dataset. Запрос прежней схемы
или несовпадение
калибровки bot/worker закрываются с ошибкой и не используют текущий кеш.
Leases не дают удалить исходный run во время расчёта. TTL, лимиты
записей, потолок диска проекта и резервы свободных bytes/inode ограничивают
staging, completed, leased и temporary state.

У принадлежащего боту научного directional-кеша и принадлежащего сайту
каталога визуализаций разные жизненные циклы. Как только независимый сайт видит
готовую задачу через внутренний API, он сохраняет результат как атомарно
опубликованный gzip JSON в `/opt/docker/site-astrosferum/data/astrodome`, не
ожидая браузера или отдельной архивной задачи. PostgreSQL хранит только
привязанные к владельцу метаданные, digest, точное имя созданного файла и срок
истечения, но не научный payload. Последний успешный расчёт для того же
авторизованного пользователя и канонических координат атомарно заменяет
прежний указатель каталога и начинает новый срок **ровно 96 часов** с момента
успешного архивирования. Задача в очереди, ошибка или отменённый повторный
расчёт не меняют срок и не заменяют готовую визуализацию. При чтении сервер
заново проверяет владельца и срок. При старте и затем каждый час maintenance
удаляет истёкшие строки и только соответствующие им проверенные точные файлы,
после чего убирает внутренне именованные orphan-файлы прерванной публикации.
Поэтому кеш браузера не является ни хранилищем, ни механизмом авторизации.

Одна явно помеченная запись `admin_fixture` является узким исключением: у неё
нет срока истечения, она исключена из очистки и обычной пользовательской
замены и показывается каждому неавторизованному посетителю и каждому текущему
настроенному администратору Telegram. Авторизованный пользователь без прав
администратора не может увидеть или открыть её и получает только свои
96-часовые результаты. Анонимный режим разрешает лишь чтение фикстуры и не
открывает сохранённые точки, создание, статус или отмену задач и результаты
других владельцев. Фикстура, декодер сохранённых визуализаций,
текущие writer, калькулятор, браузер и кеш принимают только v29/v23 с явно
поддерживаемым закреплённым профилем сетки; production web-writer использует
`production-v2`. Старая фикстура не мигрируется и не
переинтерпретируется: её должен заменить успешный расчёт текущего контракта.
Высокое качество сериализуется как `good`.
Если успешно сохранённый набор имеет канонические координаты фикстуры, при
повышении точные дроби `unavailable / total` сравниваются перекрёстным
умножением целых чисел. Общая бессрочная фикстура атомарно заменяется при
меньшей или равной доле недоступных узлов; только строго худший,
некорректный, ошибочный или отменённый результат её не меняет. Повышение не
зависит от обычной 96-часовой копии запросившего администратора.

Web-процесс также сверяет ограниченный набор pending job ID с внутренним
gateway через короткие интервалы с экспоненциальным увеличением задержки.
Поэтому успешная задача архивируется, даже если пользователь закрыл страницу
до того, как браузер увидел завершение; временная ошибка gateway сохраняет и
pending-метаданные, и прежнюю готовую визуализацию.

У каталога есть неизменяемые защитные пределы: декодированный dataset и его
сохранённый gzip-член должны каждый укладываться в `128 MiB`, а весь каталог —
в `8192` файлов и `32 GiB`. Поток gzip проверяется при публикации готового
результата и сразу сохраняется сжатым. Поэтому отдельная суточная задача
сжатия/архивирования не нужна: она добавила бы второй переход состояния, не
уменьшая объём хранения.

### 30.4. Внешний сайт, идентичность и управление доступом

Отдельный частный репозиторий `site-astrosferum` владеет тонким Go gateway.
Telegram OpenID Connect создаёт серверную
сессию; переданный браузером Telegram user ID не считается доверенным. Поток
OIDC связывает `state`, nonce, PKCE, redirect origin и ожидаемый bot client,
после чего проверяет подписанный ID token. Session cookie имеет `Secure`,
`HttpOnly`, `SameSite=Lax`; меняющие состояние маршруты дополнительно требуют
same-origin CSRF. Сохранённые точки читаются, создаются и удаляются отдельной
ролью PostgreSQL с минимальными правами. Job/status/dataset проверяют владельца и отвечают `404`
на непрозрачный идентификатор другого пользователя.

У сайта есть явные языковые URL для главной (`/en`, `/ru`), кабинета
(`/{lang}/account`), отображаемых в браузере обычного прогноза и «Горизонта»
(`/{lang}/account/forecast`, `/{lang}/account/horizon`) и
интерактивного астрокупола (`/{lang}/account/sky-conditions`). Корневой адрес —
стабильный `x-default` и всегда временно перенаправляет на `/en`, а видимый переключатель языка является
обычной ссылкой между двумя эквивалентными адресами. Для текущего документа
источником языка служит URL. У авторизованного пользователя явный выбор
сохраняется в PostgreSQL как `bot_users.preferred_web_language`,
синхронизируется с активными серверными сессиями, а открытие другой локали
перенаправляет к сохранённому выбору. Язык также сохраняется в транзакции OIDC
и используется в callback. Пока внешний модуль не применил
локализацию, оболочка показывает только нейтральный знак загрузки, а элементы,
зависящие от авторизации, скрыты до ответа `/api/v1/me`. Поэтому не возникает
ни вспышки английского текста, ни ложного состояния «не авторизован».
Заголовки ссылок `alternate`/`canonical` подготавливают структуру для будущих
публичных локализованных страниц, но сейчас весь разрабатываемый сайт отдаёт
`X-Robots-Tag: noindex` и HTML-директиву `noindex`, а `/robots.txt` запрещает обход всем роботам; страницы личного кабинета
следует оставить закрытыми от индексации и после открытия публичных страниц.

Вход через Telegram намеренно находится только на главной. OIDC callback
открывает локализованный кабинет; инструментальные страницы и астрокупол не
дублируют кнопку входа. Текущая схема владения использует проверенный Telegram
ID как канонический ключ учётной записи. Токен сообщества VK не является
учётными данными VK ID для сайта и никогда не используется в этом качестве.
Безопасная привязка VK остаётся выключенной до регистрации отдельного
приложения VK ID, проверяемого authorization-code flow и уникальной связи с
provider subject.

Страницы обычного прогноза и «Горизонта» показывают результат, но не являются
вторыми реализациями науки. Защищённый CSRF-запрос с проверкой владельца идёт
через аутентифицированный внутренний gateway к нейтральному по отношению к
платформам dispatcher результатов. Обычная задача использует те же
`ForecastQueue`, источники, калибровку, статистику и научную подготовку, что и
запрос в боте; готовая полная запись render-cache может отдать побитово тот же
JSON, а при website-only cache miss PNG намеренно не растеризуются. Для
«Горизонта» текущий run ICON-EU и модельная
высота поверхности определяются под той же очередью модельных запросов, после
чего используются те же per-user проверки, cache, общая directional FIFO и
renderer, что и для подписанной кнопки бота. Уже подготовленные значения бот
сериализует в версионированный JSON `forecast-interactive-v1` или
`horizon-interactive-v1`: браузер не повторяет формулы и не интерполирует
готовый результат. Погода, облачная преграда и Overall сохраняют одну
независимую нативную почасовую ось, а pressure-level продукты
ветра/сдвига/сиинга — отдельную независимую нативную трёхчасовую ось; ни одна
ось не ресемплируется из другой. Аддитивные вклады штрафов Overall сериализует
Go, а не восстанавливает JavaScript. `forecast-interactive-v1` также закрепляет
`algorithms.overall` как `overall-astronomy-index-v1`,
`algorithms.cloud_obstruction` как `effective-cloud-obstruction-v1` и передаёт
`algorithms.overall_calibration_sha256`; браузер проверяет этот provenance до
отрисовки. Отдельная диагностика Johnson-V сохраняет provenance NASA GEOS-CF
для AOD550/полного столба озона и не переинтерпретируется как множитель
Overall. `horizon-interactive-v1` закрепляет `artifact_key` кеша «Горизонта», модельную
высоту поверхности наблюдателя, provider/run/grid ICON-EU, версию научного
расчёта и канонический SHA-256 калибровки Overall. Первый кадр соответствует
`f000`, а все 73 сериализованных кадра сохраняют точную часовую исходную ось.
Непрерывные рассчитанные на сервере интервалы фаз Солнца покрывают
`f000−30 мин .. f072+30 мин` и получаются тем же поиском границ с шагом пять
минут, что и статический график. Координатор передаёт точный ключ научного кеша
через протокол worker; worker обязан пересчитать тот же ключ до публикации.
Браузер может перевести переданную долю confidence в проценты для отображения,
но не вычисляет научную confidence или категорию качества.
Внутренние нечисловые заглушки становятся JSON `null`, но никогда не нулём;
оси сохраняют UTC-моменты и IANA-зону координат. Dispatcher
публикует принадлежащие пользователю статус и файлы и хранит завершённый
результат ровно 96 часов. Каждый запрос статуса, отмены и файла заново
проверяет владельца; другой владелец получает `404`. Telegram и VK продолжают
получать существующие PNG без потерь.

Для обычного прогноза и «Горизонта» действуют раздельные ограниченные admission,
которые не допускают одновременно две web-задачи одного типа одного владельца,
а затем передают работу существующим очередям прогноза и направленных расчётов.
Второго downloader, формульного пути или renderer не появляется. Web-facade
использует базовый messenger без внешней отправки и отдельный capture messenger
для каждой задачи, поэтому запрос сайта не может обратиться к Telegram или VK.
Платформенные адаптеры сохраняют независимые схемы доставки, а бот продолжает
работать при полном отсутствии сайта.

Rollout-переключатель имеет узкую семантику:

- `ASTRO_ASTRODOME_ENABLED=true` разрешает функцию всем авторизованным через
  Telegram OIDC пользователям;
- `false` оставляет контролируемый доступ только ID из `ASTRO_TELEGRAM_ADMIN_IDS`;
- `false` и пустой список администраторов запрещают доступ всем.

Это не выключатель загрузчика или worker. Одинаковое правило применяется и в
web, и в bot admission; рассогласование закрывает доступ.

### 30.5. Внешний рендерер браузера и edge

Клиент без внешних зависимостей до отрисовки проверяет cardinality, порядок,
версии, digest геометрии, конечность значений, nullable-состояния и timestamps.
Основное представление — WebGL2 изнутри купола; Canvas 2D и HTML-таблица дают
эквивалентный fallback. Ячейка использует точное значение своего узла и
фиксированную количественную палитру. Сетка, компас, подсветка выбора и
астрономический декор являются только визуальными подсказками и не меняют цвет
данных. Звёздный фон находится позади научной сетки. WebGL также показывает обычную подпись
высоты `0°` без отдельно нарисованной линии горизонта, окрашенный по сумеркам, но не содержащий данных
пояс `0°…10°` и вращающуюся декоративную панораму рельефа ниже него; ни один из этих элементов не
является поверхностью ICON или расчётной ячейкой. Кольцо `10°` и подписи `0°`/`10°` оформлены так же,
как остальные высотные ориентиры, а поясняющий текст по-прежнему указывает `10°` как границу расчёта.
На странице виден ровно один инспектор выбранной
ячейки, а его дубликат live-region доступен только экранному диктору. В полноэкранном режиме тот же инспектор
и существующая почасовая шкала перемещаются внутрь купола, а при выходе возвращаются на свои места,
поэтому ни значения, ни выбранный срок прогноза не получают второго независимого состояния.
В полноэкранном режиме шкала автоматически остаётся ниже области просмотра,
пока указатель не попадёт в нижнюю часть купола; наведение на саму шкалу или
клавиатурный фокус удерживает её видимой, а на устройствах без hover шкала
остаётся видимой постоянно. Восемь физических полей и полей статуса имеют встроенные выноски с
одинаковыми пояснениями `ru`/`en`. Кнопки представления и полноэкранного режима размещены вне
компаса и в обычном, и в полноэкранном layout. Сохраняются keyboard/touch,
focus, contrast и reduced-motion.

`alice-bg` завершает публичный TLS и проксирует запрос к ограниченному по
source IP TLS origin на `dragon-he` с проверкой закреплённого сертификата;
origin передаёт его web-контейнеру через loopback. Web обращается только к
внутреннему gateway бота и не может напрямую достигнуть worker или model
store. Порядок развёртывания, файлы секретов, минимальные права БД, проверка
nginx и health probes описаны в частном репозитории `site-astrosferum`.

### 30.6. Текущее состояние rollout

Сетка, физика, контракты acquisition и общая граница coordinator/worker
реализованы здесь. OIDC/session/CSRF, API сайта, WebGL2/Canvas-клиент и
deployment templates реализованы в частном `site-astrosferum`, а контролируемый сайт с
анонимной эталонной визуализацией только
для чтения развёрнут. Текущий
записывающий контракт — production-v2/v29/v23; его полный release-прогон
фиксируется только после неизменяемого полного перерендеринга. Предшествующий
baseline v28/v22 охватил 9 288 узло-часов за 33 мин 14 с, из которых 9 284
были доступны. Первое
пятичасовое сравнение с более мелкими сетками выявило существенную
дискретизацию на малых высотах, поэтому до публичного доступа нужны критерии
приёмки по нескольким точкам и циклам. Повторные холодные/тёплые измерения
CPU/RSS/disk/payload, итоговые edge/origin
security probes, проверка отсутствия регрессии обычного прогноза, rollback
smoke test и наблюдательная валидация остаются воротами перед публичным
доступом.
